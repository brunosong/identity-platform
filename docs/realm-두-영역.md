# realm, 두 영역

직원과 고객을 가르는 선. 이 저장소에서 가장 깊은 곳까지 내려가는 개념이다.

## 왜 나누나

한 서비스가 직원과 고객을 모두 상대한다. 둘은 **같은 이름을 써도 다른 사람**이어야 하고,
한쪽의 자격증명으로 다른 쪽에 들어갈 수 없어야 한다.

```
ADMIN    직원이 산다. 식별자는 사번 성격의 값
PORTAL   고객이 산다. 식별자는 채번한 UUID
```

realm 이 하나 더 있다. `MASTER` 는 auth 를 운영하는 관리자가 사는 곳으로, Keycloak 의 master 와
같은 자리다. 직원도 고객도 아니라 이 문서가 다루는 선 밖에 있다([운영 화면 로그인](운영-화면-로그인.md)).

계정이 갈리는 것으로 끝이 아니다. 역할, 권한, URL 규칙, 토큰의 서명키까지 이 선을 따라 갈린다.

## 파티션 키는 이것 하나다

전에는 선이 둘이었다. identity 쪽은 `subject_type`(EMPLOYEE/CUSTOMER)으로, authz 쪽은
`realm`(ADMIN/PORTAL)으로 행을 나눴는데 **두 값은 끝까지 1:1 이었다.** 같은 분할선에 이름이
둘이었을 뿐이고, 그 사이 변환 코드는 항등 함수였다.

하나로 모으고 얻은 것은 **두 쪽이 같은 단어를 쓰게 된 것**이다. 값을 변환 없이 바로 비교한다.

한 realm 안에서 주체를 더 갈라야 할 날이 와도(포털에 개인·법인) **두 번째 파티션 키를 만들지
않는다.** 속성이나 그룹으로 가른다. 파티션 키를 늘리면 유일 제약, 조회 범위, 인덱스가 전부
그것을 따라가야 한다.

## 무엇이 격리를 지키나

세 겹이다. 하나가 뚫려도 다음이 받는다.

```
1. 서명키   realm 마다 키페어가 다르다. 검증은 그 realm 의 공개키 하나로만 한다
2. 조회 범위  모든 자격증명 조회가 (realm, 식별자) 로 좁혀져 있다
3. 발급 주체  토큰의 realm 은 요청이 아니라 인증된 신원이 정한다
```

**1번이 제일 세다.** 검증 키를 토큰의 `kid` 로 고르지 않는다. 이 서비스는 모든 realm 의 키를
쥐고 있어서, `kid` 를 따라가면 어느 realm 의 토큰이든 서명이 통과한다. 그러면 "이 토큰이 어느
realm 것인가" 를 클레임에 물어야 하는데 클레임은 토큰이 스스로 하는 주장이다.

realm 을 먼저 정하고 그 realm 의 키 하나로만 검증하면 **realm 을 서명이 증명한다.** 다른 realm 의
토큰은 클레임을 읽어보기도 전에 죽는다.

## realm 은 비밀이 아니다

경로에 그대로 적힌다(`/realms/portal/...`). 아무나 `admin` 을 지목할 수 있다.

그래도 되는 이유는 **경로가 realm 을 주장하는 것이 아니라 검증 키를 고르기 때문**이다. 잘못
지목하면 그 키로 검증에 실패하고, 로그인이라면 그 realm 에 계정이 없어 인증이 성립하지 않는다.

다만 **숨길 수 없다는 사실이 정책을 정한다.** 직원 realm 에 셀프 가입을 열어 두면 아무나
`/realms/admin/auth?prompt=create` 로 직원 신원과 `aud=backoffice` 토큰을 얻는다. 그래서 직원
realm 은 가입이 닫혀 있다. 직원 계정은 다른 관리자가 만들고, 최초 한 명은 시드로 심는다.

## realm 은 정책 묶음이다

enum 이 값을 들고 있다. 지금은 **어떤 방식으로 스스로 가입할 수 있는가** 하나다.

| | 비밀번호 가입 | 이메일 인증번호 가입 |
|---|---|---|
| `MASTER` | 닫힘 | 닫힘 |
| `ADMIN` | 닫힘 | 닫힘 |
| `PORTAL` | 열림 | 열림 |

가입은 auth 의 가입 화면에서 한다. 로그인 화면의 회원가입 버튼과 `prompt=create` 가 그 화면을
여는데, 둘 다 이 값을 보고 닫힌 realm 에서는 열지 않는다.

켜짐/꺼짐을 따로 두지 않는다. **비어 있으면 닫힌 것**이다. 두 값을 따로 두면 "열려 있는데 방식이
없다" 는 모순된 상태가 표현된다.

**모든 정책이 realm 에 있지는 않다.** 규칙 없는 URL 을 어떻게 할지는 모든 realm 이 fail-closed 라,
값이 갈리지 않으므로 필드로 두지 않았다.

## realm 과 시스템은 다른 것이다

헷갈리기 쉬운 자리라 이름을 일부러 다르게 지었다.

```
realm    PORTAL     로그인 경로가 지목한다. 서명키가 가른다 (iss)
시스템    shop       토큰이 향하는 곳 (aud)
서비스    customer-service, order-service   시스템 안의 구성요소
```

같은 글자를 쓰면 `/realms/portal` 의 `portal` 과 `aud` 의 값이 구분되지 않는다. 자세한 것은
[토큰 흐름](토큰-흐름.md).

## 어디에 있나

| 무엇 | 어디 |
|---|---|
| realm 정의와 정책 | `auth-domain/.../domain/shared/Realm.java` |
| 경로의 realm 해석 | `auth-web/.../web/support/AuthenticationRealm.java` |
| realm 별 서명키 | `auth-application/.../identity/token/RealmSigningKeys.java` |
| realm 별 발급자 이름 | `auth-application/.../identity/token/RealmIssuers.java` |
| 토큰 검증(키를 realm 으로 고른다) | `auth-web/.../web/support/AccessTokenReader.java` |
| 제약 | 모든 표의 `realm` 컬럼과 `CHECK` (V1 에서 만들고 V9 에서 MASTER 를 더했다) |

## 아직 없는 것

- **realm 을 늘리는 길.** enum 이라 코드를 고쳐야 한다. Keycloak 처럼 realm 을 데이터로 다루려면
  키 관리와 설정이 전부 표로 내려와야 한다
- **realm 별 정책 확장.** 지금 갈리는 값은 가입 방식뿐이다. 비밀번호 규칙이나 세션 수명 같은
  것이 realm 마다 달라질 날이 오면 이 enum 이 자란다
- **realm 간 계정 연결.** 같은 사람이 직원이면서 고객일 때 두 신원은 서로를 모른다
