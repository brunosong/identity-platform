# 인가 코드 흐름

앱이 비밀번호를 보지 않고도 사람을 로그인시키는 길. 통합 로그인(SSO)이 여기서 나온다.

## 왜 바꾸나

전에는 앱이 비밀번호를 직접 받아 auth 에 내밀고 토큰을 받았다(ROPC).

| | 전 (ROPC) | 지금 (code 흐름) |
|---|---|---|
| 비밀번호를 보는 쪽 | 앱 | auth |
| 로그인 화면을 그리는 쪽 | 앱 | auth |
| 앱이 받는 것 | 토큰 | code 한 장 |
| 앱을 옮기면 | 다시 로그인 | 세션이 있으면 그냥 통과 |
| 2단계 인증, 약관 동의 | 넣을 자리가 없다 | auth 화면에서 바꾼다 |

요점은 **로그인 절차를 앱 배포 없이 바꿀 수 있다**는 것이다. 화면을 auth 가 쥐고 있어야 가능하다.

## 한눈에

```
  포털(5173)                    auth(8080)                     DB
     |                              |                           |
  1  |--- 브라우저를 보낸다 ------->|                           |
     |    /realms/portal/auth       | 등록된 앱인가             |
     |    client_id, redirect_uri   | 등록된 주소인가 ---------->| oauth_client
     |    code_challenge(해시)      |                           |
     |                              |                           |
  2  |<-- 로그인 화면 -------------|  여기서만 비밀번호를 받는다 |
     |                              |                           |
  3  |--- 아이디/비밀번호 --------->| 인증 (토큰은 아직)        |
     |    /realms/portal/auth/login | code 발급 --------------->| oauth_authorization_code
     |                              |                           |
  4  |<-- 303 ---------------------|                           |
     |    /login/callback?code=..&state=..                      |
     |                              |                           |
  5  |--- code + verifier(원본) --->| code 를 꺼내며 지운다 --->|
     |    /realms/portal/token      | 해시 대조, 토큰 발급      |
  6  |<-- access / refresh ---------|                           |
```

6 번까지 돌아간다. 앱이 토큰을 손에 쥐면 로그인이 끝난다.

## 왜 두 번 오가나

1번에서 토큰을 바로 주지 않는 이유는 **주소창에 실리는 것은 남기 때문**이다. 브라우저 기록,
리퍼러, 서버 로그에 남는다. 그래서 주소창에는 한 번 쓰고 버리는 code 만 싣고, 토큰은 별도 요청의
응답 본문으로 준다.

그러면 code 를 주운 쪽은 어떻게 막나. **PKCE** 다.

```
1번  앱: 난수(verifier)를 만들어 자기만 갖고, 해시(challenge)만 보낸다
5번  앱: 원본을 낸다.  auth: 해시해서 1번에 받아둔 값과 맞춘다
```

원본을 모르는 쪽은 code 를 주워도 토큰으로 바꾸지 못한다. 시크릿이 하던 일을 요청마다 새로 만드는
값이 대신하는 것이라, 브라우저에서 도는 앱도 시크릿 없이 안전하다.

## 지키는 규칙

- **돌아갈 주소는 미리 등록된 것만.** 문자 그대로 대조한다. 와일드카드도 접두어 일치도 없다
- **거절할 때 돌려보내지 않는다.** 주소를 못 믿는 상태에서 그 주소로 오류를 보내는 것도 배달이다
- **실패 사유를 나누지 않는다.** 모르는 앱인지 틀린 주소인지 알려주면 그것으로 찍어볼 수 있다
- **code 는 1분, 한 번.** 꺼내면서 지운다. 저장소가 내주는 읽기가 `consume` 하나뿐이다
- **교환에 실패한 code 도 태운다.** 지우는 일이 독립 트랜잭션이라 호출자가 롤백해도 되살아나지 않는다
- **토큰 응답은 명세의 모양.** `snake_case` 와 `invalid_grant`. 표준 라이브러리가 읽을 수 있어야 한다
- **PKCE 는 필수, S256 만.** `plain` 은 값을 그대로 보내므로 흉내낼 수 있다
- **비밀번호가 틀리면 앱에 알리지 않는다.** 로그인 화면을 다시 그린다

## 로컬에서 보기

```
./mvnw -pl auth-service/auth-bootstrap spring-boot:run -Dspring-boot.run.profiles=local
cd frontends/portal && npm run dev
```

`http://localhost:5173/login` 에서 [BrunoSong 로그인] 을 누른다. 앱 등록은
`http://localhost:8080/page/oauth-clients`.

## 아직 없는 것

- **SSO 세션 쿠키.** 지금은 앱을 옮길 때마다 로그인 화면이 다시 뜬다. 이 흐름의 목적 그 자체다
- **`id_token`.** 지금 나가는 것은 access / refresh 뿐이다. `nonce` 는 코드에 적어 두고만 있다
- **만료된 code 치우기.** 아무도 바꾸러 오지 않은 코드가 행으로 남는다
- **화면 보호.** auth 의 운영 화면은 세션이 없어 막을 수단이 없고, 그래서 local 에서만 뜬다
- **소셜 로그인 통합.** 구글은 아직 앱이 직접 상대한다. auth 뒤로 넣으면 앱은 구글을 모르게 된다
