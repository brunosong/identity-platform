# 인가 코드 흐름

앱이 비밀번호를 보지 않고도 사람을 로그인시키는 길. 통합 로그인(SSO)이 여기서 나온다.

## 왜 바꾸나

전에는 앱이 비밀번호를 직접 받아 auth 에 내밀고 토큰을 받았다(ROPC).

| | 전 (ROPC) | 지금 (code 흐름) |
|---|---|---|
| 비밀번호를 보는 쪽 | 앱 | auth |
| 로그인 화면을 그리는 쪽 | 앱 | auth |
| 앱이 받는 것 | 토큰 | code 한 장 |
| 앱을 옮기면 | 다시 로그인 | 세션이 있으면 그냥 통과 |
| 2단계 인증, 약관 동의 | 넣을 자리가 없다 | auth 화면에서 바꾼다 |

요점은 **로그인 절차를 앱 배포 없이 바꿀 수 있다**는 것이다. 화면을 auth 가 쥐고 있어야 가능하다.

## 한눈에

```
  포털(5173)                    auth(8080)                     DB
     |                              |                           |
  1  |--- 브라우저를 보낸다 ------->|                           |
     |    /realms/portal/auth       | 등록된 앱인가             |
     |    client_id, redirect_uri   | 등록된 주소인가 ---------->| oauth_client
     |    code_challenge(해시)      |                           |
     |                              |                           |
  2  |<-- 로그인 화면 -------------|  여기서만 비밀번호를 받는다 |
     |                              |                           |
  3  |--- 아이디/비밀번호 --------->| 인증 (토큰은 아직)        |
     |    /realms/portal/auth/login | code 발급 --------------->| oauth_authorization_code
     |                              |                           |
  4  |<-- 303 ---------------------|                           |
     |    /login/callback?code=..&state=..                      |
     |                              |                           |
  5  |--- code + verifier(원본) --->| code 를 꺼내며 지운다 --->|
     |    /realms/portal/token      | 해시 대조, 토큰 발급      |
  6  |<-- access / refresh ---------|                           |
```

6 번까지 돌아간다. 앱이 토큰을 손에 쥐면 로그인이 끝난다.

**두 번째 앱은 2, 3 을 건너뛴다.** 1 번에서 세션 쿠키가 실려 오기 때문이다.

```
  백오피스(5174)                auth(8080)
     |                              |
  1  |--- 브라우저를 보낸다 ------->| 등록된 앱인가
     |    쿠키: AUTH_SESSION        | 세션이 살아 있는가 -> 있다
  4  |<-- 303 code=.. -------------|  화면을 띄우지 않는다
```

## 새로고침하면 왜 로그아웃되나, 그리고 어떻게 되돌리나

토큰은 앱 메모리에 있다. 새로고침 한 번이면 문서가 통째로 갈리고 토큰도 같이 날아간다.
그런데 **auth 의 세션 쿠키는 그대로 살아 있다.** 더 오래 사는 쪽이 따로 있는 셈이다.

| | 어디 | 얼마 | 새로고침하면 |
|---|---|---|---|
| access 토큰 | 앱 메모리 | 2시간 | 죽는다 |
| refresh 토큰 | 앱 메모리 | 24시간 | 죽는다 |
| `AUTH_SESSION` | 브라우저 쿠키 | 8시간 | **산다** |

**앱은 그 쿠키를 읽지 못한다.** 다른 출처의 쿠키라서 `httpOnly` 를 떼도 못 읽는다. 그래서
"이 브라우저가 아직 로그인해 있는가" 를 알아내는 방법이 **인가 엔드포인트로 가 보는 것**
하나뿐이다. fetch 로는 안 된다. 리다이렉트를 값으로 받을 수 없고, code 는 주소창으로만 온다.

문제는 그냥 가 보면 세션이 없을 때 **로그인 화면이 떠버린다**는 것이다. 상품을 구경하러 온
사람이 로그인 화면에 갇힌다. 실패를 표현할 방법이 없다.

`prompt=none` 이 그 자리를 연다.

```
  포털(5173)                    auth(8080)
     |                              |
     |--- prompt=none -------------→| 세션 있음 → 303 ?code=..&state=..
     |                              | 세션 없음 → 303 ?error=login_required&state=..
     |←-----------------------------|  둘 다 리다이렉트다. 화면이 아니다
```

**실패도 리다이렉트인 것이 전부다.** 그래야 앱이 코드로 분기한다.

### 언제 시도하나

앱이 뜰 때마다 하지 않는다. 상품만 보는 사람에게는 auth 왕복이 통째로 낭비다. 토큰이 실제로
필요해지는 자리, 즉 `RequireAuth` 가 로그인 화면으로 보내기 직전에 한 번 건다.

거기에 깃발을 하나 더 본다. 로그인에 성공하면 `localStorage` 에 "이 브라우저는 전에 로그인한
적 있다" 는 표시를 남긴다. 토큰이 아니라 불리언 하나라 새어도 잃을 것이 없다. **한 번도 로그인한
적 없는 방문자는 이 깃발이 없어 왕복을 아예 하지 않는다.**

```
RequireAuth
  로그인돼 있다            → 통과
  깃발 있고 이 탭에서 처음 → 조용히 시도 (prompt=none)
  그 밖                    → /login
```

`login_required` 가 돌아오면 깃발을 내린다. 안 내리면 세션이 끝난 뒤에도 새 탭마다 헛왕복을
한 번씩 한다. 탭 단위 표시(`sessionStorage`)도 함께 두는데, 이게 없으면 세션이 정말 없을 때
시도와 `login_required` 사이를 무한히 돈다.

## 요청마다 누가 받나

| 요청 | 컨트롤러 | 하는 일 | 돌려주는 것 |
|---|---|---|---|
| `GET /realms/{realm}/auth` | `AuthorizationEndpointController` | 앱과 주소 대조, 세션 확인, `prompt` 해석 | 로그인 화면, 또는 303 (`code` 나 `error`) |
| `POST /realms/{realm}/auth/login` | `LoginSubmissionController` | **비밀번호 확인**, 세션 시작 | 303 (쿠키를 함께 심는다) |
| (둘의 공통 마무리) | `AuthorizationCodeRedirect` | **code 발급**과 저장 | `redirect_uri?code=..&state=..` |
| `POST /realms/{realm}/token` | `TokenEndpointController` | **code 검증**(1회용·만료·앱·주소·PKCE) | 토큰 JSON |
| `GET /realms/{realm}/logout` | `LogoutEndpointController` | 세션 끊기, 쿠키 지우기 | 등록된 주소로 303, 아니면 화면 |

앞의 셋은 브라우저가 오고 화면이나 리다이렉트로 답한다. 마지막 하나만 앱이 부르고 JSON 으로 답한다.

사람을 확인하는 길이 둘(비밀번호, 세션)인데 **마무리는 하나**다. 두 컨트롤러가 같은
`AuthenticatedSubject` 를 손에 쥐고 `AuthorizationCodeRedirect` 에 넘긴다. 그래서 앱 입장에서는
사람이 방금 로그인했든 아침에 했든 똑같이 보인다.

## 로그아웃은 두 겹이다

한 번 로그인이 여러 앱에 걸렸으니 로그아웃도 그래야 한다. 그런데 끊어야 할 것이 둘이다.

```
앱의 토큰       앱이 버린다. 그 앱에서만 로그아웃
auth 의 세션    /realms/{realm}/logout 으로 끊는다. 모든 앱에서 로그아웃
```

앱에서 토큰만 버리고 다시 로그인을 누르면 화면 없이 들어온다. 세션이 그대로이기 때문이다.
쇼핑몰 화면에 버튼을 둘로 나눠 둔 것이 그 차이를 보라는 것이다.

**이미 발급된 access 토큰은 죽지 않는다.** 서명만 맞으면 통하는 무상태 값이라 남은 수명 동안
살아 있다. 그것까지 막으려면 토큰을 쓸 때마다 서버에 물어보는 구조가 필요하고, 그건 무상태
토큰을 쓰는 이유를 되돌리는 일이다. 그래서 access 토큰은 짧게 둔다.

## 왜 두 번 오가나

1번에서 토큰을 바로 주지 않는 이유는 **주소창에 실리는 것은 남기 때문**이다. 브라우저 기록,
리퍼러, 서버 로그에 남는다. 그래서 주소창에는 한 번 쓰고 버리는 code 만 싣고, 토큰은 별도 요청의
응답 본문으로 준다.

그러면 code 를 주운 쪽은 어떻게 막나. **PKCE** 다.

```
1번  앱: 난수(verifier)를 만들어 자기만 갖고, 해시(challenge)만 보낸다
5번  앱: 원본을 낸다.  auth: 해시해서 1번에 받아둔 값과 맞춘다
```

원본을 모르는 쪽은 code 를 주워도 토큰으로 바꾸지 못한다. 시크릿이 하던 일을 요청마다 새로 만드는
값이 대신하는 것이라, 브라우저에서 도는 앱도 시크릿 없이 안전하다.

## 지키는 규칙

- **돌아갈 주소는 미리 등록된 것만.** 문자 그대로 대조한다. 와일드카드도 접두어 일치도 없다
- **거절할 때 돌려보내지 않는다.** 주소를 못 믿는 상태에서 그 주소로 오류를 보내는 것도 배달이다
- **실패 사유를 나누지 않는다.** 모르는 앱인지 틀린 주소인지 알려주면 그것으로 찍어볼 수 있다
- **code 는 1분, 한 번.** 꺼내면서 지운다. 저장소가 내주는 읽기가 `consume` 하나뿐이다
- **교환에 실패한 code 도 태운다.** 지우는 일이 독립 트랜잭션이라 호출자가 롤백해도 되살아나지 않는다
- **토큰 응답은 명세의 모양.** `snake_case` 와 `invalid_grant`. 표준 라이브러리가 읽을 수 있어야 한다
- **PKCE 는 필수, S256 만.** `plain` 은 값을 그대로 보내므로 흉내낼 수 있다
- **비밀번호가 틀리면 앱에 알리지 않는다.** 로그인 화면을 다시 그린다
- **세션 쿠키는 auth 에만 간다.** 경로가 `/realms/{realm}` 이라 앱도 `/api/**` 도 못 본다
- **세션은 8시간, 연장 없다.** 쓸 때마다 늘리면 언제 끝나는지를 여러 곳이 정하게 된다
- **세션 확인은 요청 검증 다음.** 순서가 바뀌면 등록되지 않은 앱의 요청에 코드가 나간다.
  `login_required` 를 앱 주소로 돌려보낼 수 있는 것도 이 순서 덕분이다
- **아는 `prompt` 는 `none` 하나.** 나머지는 400 이다. 조용히 무시하면 `prompt=login` 으로
  재인증을 요구한 쪽이 다시 물었다고 믿는데 실제로는 세션이 그대로 통과한다
- **`prompt` 가 정하는 것은 세션이 없을 때뿐.** 있을 때는 어느 쪽이든 코드를 내준다
- **조용한 시도는 탭마다 한 번.** 표시가 없으면 세션이 없을 때 무한히 왕복한다
- **로그아웃 뒤 돌아갈 주소도 등록된 것만.** 지금은 로그인 주소 목록을 그대로 쓴다
- **로그아웃은 거절이 흐름을 막지 않는다.** 주소가 틀려도 세션은 이미 끊겼다

## 아직 없는 것

- **뒷채널 로그아웃.** 한 앱에서 로그아웃해도 다른 앱은 자기 토큰을 계속 들고 있다. 앱들에게
  알려주는 길(back-channel logout)이 없다
- **로그아웃용 주소 목록.** 로그인 주소와 같은 표를 쓴다. 그 목록에 있는 주소는 인가 코드도
  받을 수 있으므로, 엄밀히는 갈라야 한다
- **`id_token`.** 지금 나가는 것은 access / refresh 뿐이다. `nonce` 는 코드에 적어 두고만 있다
- **만료된 code 와 세션 치우기.** 쓰이지 않은 행이 그대로 남는다
- **화면 보호.** auth 의 운영 화면은 세션이 없어 막을 수단이 없고, 그래서 local 에서만 뜬다
- **소셜 로그인 통합.** 구글은 아직 앱이 직접 상대한다. auth 뒤로 넣으면 앱은 구글을 모르게 된다
- **401 을 받았을 때의 자동 복구.** `http.js` 에 401 을 가로채는 자리가 없다. access 토큰이
  만료된 채로 customer-service 를 부르면 화면에 오류만 뜬다. 조용한 시도를 여기에도 걸면 된다
- **로그인 전에 보던 자리로 돌아오기.** 조용한 시도는 돌아갈 자리를 기억하지만, 사람이 로그인
  버튼을 눌러 들어온 경우는 아니다. 상세 화면에서 로그인하면 마이페이지로 간다
- **리프레시 토큰 정리.** 조용한 시도가 생기면서 하는 일이 겹친다. 게다가 세션(8시간)보다
  오래 살고(24시간) 회전이 없어 로그아웃해도 안 죽는다. 걷어내거나 회전을 붙여야 한다
