# 이메일 인증번호

비밀번호 없이 이메일로 6자리 숫자를 받아 로그인하는 길. auth 의 로그인 화면에 있다.

## 왜 있나

비밀번호를 안 만들어도 되는 길이 하나 필요하다. 직원(`ADMIN` realm)은 비밀번호 계정 자체를
갖지 않아서 이것이 유일한 로그인 수단이고, 고객은 비밀번호와 이 방식 중 고를 수 있다.

메일함을 여는 사람이 그 주소의 주인이라는 것이 전제다. 그래서 같은 장치가 두 가지 일을 한다.

```
로그인   등록된 주소에만 보낸다          "이 주소의 주인이 맞나"
가입     등록되지 않은 주소에만 보낸다    "이 주소가 정말 당신 것인가"
```

가입 쪽은 가입 화면에 있다([회원가입](회원가입.md)). 직원 realm 은 셀프 가입이 닫혀 있어서
가입용 번호도 나가지 않는다.

| | 전 | 지금 |
|---|---|---|
| 번호를 받는 쪽 | 앱이 받아 `/api/auth/realms/{realm}/login/email-otp` 로 전달 | auth 의 로그인 화면 |
| 확인이 끝나고 나가는 것 | 토큰 | 로그인 세션과 code 한 장 |

## 한눈에

```
  브라우저                           auth                          DB / 메일
   |                                  |                              |
   |-- POST /realms/{realm}/auth/send-code                           |
   |   email, 인가 요청(hidden)        | 등록된 주소인가, 1분 내 발송인가 |
   |                                  | 6자리 난수, 해시해서 저장 ----->| identity_email_otp
   |                                  | 메일 발송 ------------------->| (로컬은 로그로 대신)
   |<-- 번호 칸이 열린 로그인 화면 -----| (보냈든 말든 같은 화면)          |
   |                                  |                              |
   |-- POST /realms/{realm}/auth/login/otp                           |
   |   email, code                    | 최신 미사용 챌린지, 차단·만료·해시 |
   |                                  | 쓴 것으로 표시, 이메일 확인됨     |
   |<- 303 redirect_uri?code=&state=--| 세션 쿠키 심기, code 발급        |
```

## 왜 그렇게 도나

**화면이 늘 같다.** 번호를 달라는 요청에는 보냈든 안 보냈든 번호 칸이 열린 같은 화면으로 답한다.
쿨다운에 걸려도, 등록되지 않은 주소여도 같다. 다르게 답하면 주소를 넣어보는 것만으로 가입자
명단을 만들 수 있다. 보낼지 말지는 유스케이스가 정하고 컨트롤러는 가르지 않는다.

**인증과 발급이 갈려 있다.** `EstablishEmailOtpAuthenticationUseCase.withEmailOtp()` 는 "누가
로그인했나" 까지만 확정한다. 토큰은 앱이 code 를 바꿀 때 나간다. 틀리면 번호 칸이 열린 채로
화면을 다시 그리고(401) 앱에 알리지 않는다.

**번호를 받아낸 것이 소유의 증명이다.** 관리자가 만든 직원 계정처럼 확인되지 않은 채 남아 있던 이메일이
이 로그인에 성공하면 확인됨으로 올라간다.

## 번호를 지키는 네 가지

```
수명       5분
시도       5회 틀리면 그 챌린지는 죽는다. 새로 받아야 한다
재발송     같은 주소로 60초 안에 다시 보내지 않는다
저장       해시로 저장한다. 원문은 메일에만 있다
```

6자리를 해시해 봐야 백만 가지라 뒤집을 수는 있다. 그래도 해시로 두는 것은 DB 를 들여다본
사람이 그 자리에서 바로 로그인하지 못하게 하려는 것이고, 5분 수명이 그 계산 시간과 맞물린다.
시도 횟수는 독립 트랜잭션에서 올린다. 틀리면 예외로 끝나 트랜잭션이 되돌아가는데, 횟수까지
되돌아가면 5회 제한이 걸리지 않는다.

`local` 프로파일에서는 번호가 `123456` 으로 고정되고 발송 대신 로그에 찍힌다.

## 지키는 규칙

- **번호는 앱을 거치지 않는다.** 받는 곳은 auth 의 로그인 화면 하나다
- **보낼지 말지는 부르는 쪽(유스케이스)이 판단한다.** 발급기는 "오면 보낸다" 만 한다
- **한 이메일에 살아 있는 챌린지는 최신 하나.** 검증은 늘 최신 미사용 건을 본다
- **쓴 번호는 쓴 것으로 표시한다.** 같은 번호로 두 번 들어오지 못한다
- **챌린지에 용도 표시가 없다.** 로그인용과 가입용의 조건이 서로 배타적이라(등록됨, 등록 안 됨)
  한 주소가 동시에 양쪽 대상이 될 수 없다

## 어디에 있나

| 무엇 | 어디 |
|---|---|
| 로그인 화면(번호 폼) | `auth-web/src/main/resources/templates/oauth/login.html` |
| 발송, 번호 확인, 세션, code | `auth-web/.../web/authorize/OtpLoginController.java` |
| 로그인용 발송 판단 | `auth-application/.../identity/service/RequestEmailOtpService.java` |
| 인증까지만 하는 흐름 | `auth-application/.../identity/service/AuthenticateWithEmailOtpService.java` |
| 발급(쿨다운, 수명, 로컬 고정번호) | `auth-application/.../identity/service/EmailOtpIssuer.java` |
| 검증(만료, 시도 제한) | `auth-application/.../identity/service/EmailOtpVerifier.java` |
| 챌린지 규칙 | `auth-domain/.../domain/identity/EmailOtpChallenge.java` |
| 시도 기록(독립 트랜잭션) | `auth-dataaccess/.../identity/adapter/EmailOtpStoreAdapter.java` |
| 표 | `identity_email_otp` (V1) |

## 아직 없는 것

- **만료된 챌린지 치우기.** 쓰이지 않은 행이 그대로 남는다
- **발송 실패 처리.** 메일이 나가지 않아도 화면은 보냈다고 말한다
- **주소당 하루 발송 한도.** 60초 쿨다운만 있어서, 하루 종일 1분 간격으로 보내는 것은 막지 못한다
- **직원 로그인 화면에서 비밀번호 폼 숨기기.** 직원은 비밀번호 계정이 없는데 로그인 화면은
  realm 과 상관없이 비밀번호 폼도 그린다
