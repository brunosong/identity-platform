# 소셜 로그인

구글 계정으로 들어오는 길. 우리는 비밀번호를 받지 않고, 구글이 확인한 사람을 넘겨받는다.

## 왜 있나

비밀번호를 만들지 않아도 되고, 비밀번호를 지키는 일(해시, 잠금, 재설정, 유출 대응)의 상당
부분을 구글이 대신한다. 사용자 쪽에서도 가입 단계가 버튼 하나로 줄어든다.

대신 두 가지를 우리가 떠안는다. **구글이 돌려보낸 사람이 진짜인지 확인하는 일**과, **그 사람이
우리 쪽의 누구인지 잇는 일**이다.

## 한눈에

```
  브라우저                우리(auth)                  구글
     |                       |                         |
  1  |-- 로그인 버튼 -------->|                         |
     |                       |-- state 를 쿠키에 담고 --|
     |<------------------------ 구글 로그인 화면으로 ---|
  2  |-- 구글에서 로그인 ------------------------------>|
     |<-- code 를 달고 돌아온다 ------------------------|
  3  |-- code ------------->|                         |
     |                      |-- code + 우리 시크릿 --->|  (서버 대 서버)
     |                      |<-- id_token, 이메일 -----|
     |                      | 계정 잇기 / 만들기        |
  4  |<-- 우리 토큰 --------|                          |
```

3번이 요점이다. **code 를 토큰으로 바꾸는 일은 서버가 한다.** 구글이 우리 앱에 발급한 시크릿을
브라우저에 둘 수 없기 때문이고, 그래서 브라우저를 다녀온 code 만으로는 아무도 남의 계정에
들어가지 못한다.

## 돌아오는 자리가 둘이다

같은 흐름인데 구글이 브라우저를 돌려보내는 주소가 두 벌 살아 있다. 갈리는 것은 교환 요청에
적는 `redirect_uri` 하나뿐이고, `SocialCallback`(BROKER/APP) 이 어느 쪽인지 말한다.

| | BROKER | APP |
|---|---|---|
| 돌아오는 주소 | `8080/realms/portal/broker/google/endpoint` | `5173/callback` |
| 받는 곳 | `GoogleBrokerController` | `AuthSocialLoginApiController` |
| `state` 검사 | 서버(쿠키 `SOCIAL_STATE`) | 앱(`sessionStorage`) |
| 앱이 구글을 아나 | 모른다 | 안다(`portal/src/api/google.js`) |

**BROKER 쪽이 제 모습이다.** 구글 콘솔에 등록할 주소가 하나로 끝나고, 앱이 몇 개가 되든 구글
설정은 그대로다. 프론트엔드는 구글이라는 것이 있는지도 모른다. Keycloak 이 `broker/{provider}`
로 하는 일과 같다.

APP 쪽은 앱이 구글 주소와 `client_id` 를 직접 알아야 한다. 지금 포털 화면이 이쪽으로 돈다.
[인가 코드 흐름](인가-코드-흐름.md)이 자리를 잡으면 이 경로는 사라진다.

## 계정을 어떻게 잇나

```
이미 연결된 소셜 계정이면        그 신원으로 발급
처음 보는 소셜 계정이면
  확인된 이메일과 같은 신원이 있나
     있으면  그 신원에 소셜 수단만 더한다     <- 자동 연결
     없으면  신원을 새로 만든다
```

**자동 연결은 확인된 이메일(`email_verified`)에만 적용한다.** 그 조건이 빠지면 남의 이메일을
자기 소셜 계정에 적어두는 것만으로 그 사람의 신원을 가져갈 수 있다.

그래서 비밀번호로 가입했던 사람이 나중에 구글로 들어와도 계정이 둘로 갈리지 않는다. 같은
신원에 로그인 수단이 하나 늘 뿐이다.

## id_token 서명은 검증하지 않는다

받은 `id_token` 의 서명을 구글 공개키로 확인하지 않는다. 그 토큰을 **우리가 TLS 로 구글
토큰 엔드포인트에 직접 물어 받은 응답**이라 중간에 위조가 낄 자리가 없기 때문이다. OIDC Core
3.1.3.7 도 이 경우를 예외로 둔다.

확인하는 것은 따로 있다.

```
iss              구글이 맞나
aud              우리 앱에 발급된 것이 맞나
exp              만료되지 않았나
email_verified   확인된 이메일인가
```

`aud` 를 보는 것이 특히 중요하다. 없으면 **다른 앱에 발급된 토큰**을 들고 와도 통과한다.

## 지키는 규칙

- **state 는 한 번 쓰고 버린다.** 막는 것은 로그인 CSRF 다. 공격자가 자기 계정으로 시작한
  콜백 주소를 피해자에게 열게 하면, 피해자 브라우저가 공격자 계정으로 로그인된다
- **state 쿠키는 `SameSite=Lax`.** 구글이 브라우저를 밀어 보내는 최상위 이동에 실려야 한다
- **시크릿은 저장소에 없다.** `application-local.yml` 에 있고 그 파일은 추적되지 않는다
- **provider 설정이 비어 있으면 소셜 로그인이 꺼진 채로 뜬다.** 아무 값이나 들고 구글에 붙는
  것보다 "로그인이 안 된다" 가 낫다

## 어디에 있나

| 무엇 | 어디 |
|---|---|
| 브로커(보내기, 돌아오기) | `auth-web/.../web/broker/GoogleBrokerController.java` |
| 앱 콜백을 받는 API | `auth-web/.../web/client/identity/AuthSocialLoginApiController.java` |
| 계정 잇기, 발급 | `auth-application/.../identity/service/AuthenticateWithSocialService.java` |
| 구글과의 통신 | `auth-social/.../social/google/` |
| 앱 쪽 시작점(APP 방식) | `frontends/portal/src/api/google.js` |
| 표 | `identity_social_account` (V1) |

## 아직 없는 것

- **`id_token` 의 JWKS 검증.** 지금 경로에서는 명세상 선택이라 미뤘다. 브로커가 아닌 경로로
  토큰을 받게 되는 날 필요해진다
- **연결 해제.** 소셜 수단을 떼어낼 길이 없다
- **연결 화면.** 확인되지 않은 이메일로 가입한 계정은 자동 연결이 막히는데, 사람이 직접 잇는
  화면이 없어 막다른 길이 된다
- **구글 말고.** 다른 provider 를 붙일 자리(`SocialProvider`)는 있지만 구현은 구글뿐이다
- **code 흐름과의 통합.** 로그인 화면(`/realms/{realm}/auth`)에 구글 버튼이 없다. 붙으면 앱은
  구글을 아예 모르게 된다
