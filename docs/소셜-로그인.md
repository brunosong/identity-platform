# 소셜 로그인

구글 계정으로 들어오는 길. 우리는 비밀번호를 받지 않고, 구글이 확인한 사람을 넘겨받는다.
구글 버튼은 앱이 아니라 auth 의 로그인 화면에 있다. 앱은 구글이라는 것이 있는지도 모른다.

## 왜 이렇게 하나

| | 전 | 지금 |
|---|---|---|
| 구글 버튼 | 앱 화면 (`portal/src/api/google.js`) | auth 로그인 화면 |
| 구글이 돌려보내는 곳 | 앱(`5173/callback`)과 auth 두 벌 | auth 한 곳 |
| 앱이 받는 것 | 우리 토큰 (`/api/auth/.../login/social`) | 다른 로그인과 같은 code 한 장 |
| 구글 콘솔 등록 주소 | 앱마다 하나씩 | 하나 |

전에는 앱이 구글 주소와 `client_id` 를 알고, 구글에서 받은 code 를 우리 API 에 넘겨 토큰을
받았다. 앱이 늘 때마다 구글 설정이 늘고, 토큰을 곧바로 내주는 API 가 따로 있어야 했다.
지금은 Keycloak 의 `broker/{provider}` 처럼 auth 가 구글의 클라이언트가 된다.

## 한눈에

```
  브라우저              auth                                     구글
     |                    |                                        |
  1  |-- 로그인 화면 [구글] -> /broker/google/login?인가 요청      |
     |                    | 요청 검증, 쿠키 둘(state, 되돌아갈 요청) |
     |<-- 구글로 ----------|                                        |
  2  |-- 구글에서 로그인 --------------------------------------------->|
     |<-- code 를 달고 /broker/google/endpoint 로 --------------------|
  3  |------------------->| code + 우리 시크릿 (서버 대 서버) ------->|
     |                    |<-- id_token, 이메일 ----------------------|
     |                    | 계정 잇기/만들기, 로그인 세션 심기         |
  4  |<-- /realms/portal/auth?원래 인가 요청 으로 되돌림               |
  5  |-- 그 주소로 ------>| 세션이 있으니 화면 없이 code 발급          |
     |<-- 앱 주소?code=.. |                                           |
```

## 왜 그렇게 도나

**4번에서 code 를 직접 내주지 않는다.** 인가 요청의 입구로 되돌려 보낸다. 세션이 생겼으니
입구가 "이미 로그인한 브라우저" 로 보고 code 를 내준다. code 를 내주는 길이 하나로 남아서
요청 검증과 발급 규칙이 구글 경로에서 따로 갈라지지 않는다.

**쿠키가 둘인 이유.** `SOCIAL_STATE` 는 구글에서 돌아온 콜백이 이 브라우저가 시작한 것인지
가린다(로그인 CSRF). `SOCIAL_RESUME` 은 구글에 다녀온 뒤 되돌아갈 인가 요청이다. 주소 전체가
아니라 질의만 담고 경로는 서버가 붙인다. 쿠키 값으로 주소를 정하면 아무 데로나 보내는 길이 된다.

**3번에서는 인증까지만 한다.** 토큰은 나가지 않는다. 앱이 code 를 바꿀 때 나간다.

## 계정을 어떻게 잇나

```
이미 연결된 구글 계정이면       그 신원으로 로그인
처음 보는 구글 계정이면
  구글이 확인한 이메일이 없으면  거절
  같은 이메일의 신원이 있나
     있고, 우리 쪽도 확인된 이메일  그 신원에 구글 수단만 더한다  (자동 연결)
     있지만 우리 쪽이 미확인        거절. 기존 방법으로 로그인한 뒤 연결하라고 안내
     없으면                         신원을 새로 만든다
```

**양쪽 다 확인된 이메일이어야 잇는다.** 구글 쪽이 빠지면 남의 이메일을 적은 구글 계정으로 그 사람의
신원을 가져간다. 우리 쪽이 빠지면 pre-account hijacking 이다. 공격자가 남의 주소로 미확인 계정을
심어두면, 피해자가 구글로 처음 들어올 때 공격자의 신원에 붙는다.

## 지키는 규칙

- **포털에서만 연다.** 소셜은 처음 온 사람에게 신원을 만들어 준다. 직원 realm 에서는 404 다
- **등록되지 않은 앱의 요청은 구글에 보내지 않는다.** 떠나기 전에 인가 요청을 검증한다
- **state 는 한 번 쓰고 버린다.** 콜백을 받으면 쿠키 둘을 지운다
- **쿠키는 `SameSite=Lax`, HttpOnly, 5분.** 구글이 밀어 보내는 최상위 이동에 실려야 한다
- **구글에서 취소하면 세션 없이 되돌린다.** 입구가 로그인 화면을 다시 그린다
- **id_token 서명은 확인하지 않는다.** 우리가 TLS 로 구글 토큰 엔드포인트에 직접 물어 받은
  응답이라 위조가 낄 자리가 없다(OIDC Core 3.1.3.7). `iss`, `aud`, `exp`, `email_verified` 는 본다
- **시크릿은 저장소에 없다.** `application-local.yml` 에 있고 그 파일은 추적되지 않는다
- **설정이 비어 있으면 소셜이 꺼진 채로 뜬다.** 브로커 경로가 404 가 된다

## 어디에 있나

| 무엇 | 어디 |
|---|---|
| 브로커(보내기, 돌아오기, 되돌리기) | `auth-web/.../web/broker/GoogleBrokerController.java` |
| 로그인 화면의 구글 버튼 | `auth-web/src/main/resources/templates/oauth/login.html` |
| 인증까지만 하는 포트 | `auth-application/.../identity/ports/in/EstablishSocialAuthenticationUseCase.java` |
| 계정 잇기/만들기 | `auth-application/.../identity/service/AuthenticateWithSocialService.java` |
| 세션 심기 | `auth-web/.../web/authorize/LoginSessionStarter.java` |
| 구글과의 통신, 돌아올 주소 | `auth-external/.../external/google/` |
| 표 | `identity_social_account` (V1) |
| 흐름 전체 테스트 | `auth-bootstrap/.../GoogleBrokerIntegrationTest.java` |

통합 테스트는 구글에 신원을 묻는 어댑터 하나만 대역으로 바꾸고 나머지는 진짜로 돈다. 구글 버튼에서
code, id_token 의 `nonce` 까지 이어지는지 본다.

## 아직 없는 것

- **구글에 보내는 `nonce`.** 서버 대 서버로 받는 토큰이라 명세상 선택이라 미뤘다
- **id_token 의 JWKS 검증.** 브라우저가 id_token 을 직접 건네는 경로(원탭 같은 것)가 생기면 필수다
- **연결 해제와 연결 화면.** 미확인 이메일로 가입한 계정은 자동 연결이 막히는데, 사람이 직접 잇는
  화면이 없어 막다른 길이 된다
- **구글 말고.** 다른 provider 를 붙일 자리(`SocialProvider`)는 있지만 구현은 구글뿐이다
