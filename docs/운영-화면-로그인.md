# 운영 화면 로그인

auth 자신의 화면(`/page/**`)에 들어가려면 MASTER realm 관리자로 로그인해야 한다. Keycloak 의 관리
콘솔이 master realm 에 로그인하는 것과 같은 모양이다.

## 왜 이렇게 하나

| | 전 | 지금 |
|---|---|---|
| 운영 화면을 막는 것 | 없음. local 프로파일에서만 떠서 버텼다 | MASTER 로그인 |
| 누가 들어오나 | 주소를 아는 누구나 | MASTER 계정 (`admin`) |
| 로그인 방식 | 없음 | 다른 앱과 같은 code + PKCE 흐름 |
| 토큰을 어디 두나 | 없음 | `HttpOnly` 쿠키. 서버는 아무것도 기억하지 않는다 |
| 지키는 범위 | 없음 | 8080 전체. `/realms`, `/api`, `/.well-known` 만 뺀다 |

직원(ADMIN)과 따로 MASTER 를 둔 것은 Keycloak 과 같은 이유다. auth 를 운영하는 사람과 업무
시스템을 쓰는 직원은 다른 사람이다. realm 은 표가 아니라 enum 에 값 하나를 더했다.

## 한눈에

```
 브라우저                        운영 화면(/page, /)              로그인 서버(/realms/master)
 로그인
  1 GET /page/roles ----------> 쿠키에 access 없음
                                 CONSOLE_LOGIN 쿠키(state, PKCE 원본)
  2 <-- 302 /realms/master/auth?client_id=auth-console&code_challenge=..
    ---------------------------------------------------------> AUTH_SESSION 있으면 화면 없이 통과
  3 <-- 303 /page/login/callback?code=..&state=.. ------------ 없으면 로그인 화면, admin/admin
  4 GET callback ------------> state 대조, code 교환(같은 프로세스)
                                 CONSOLE_ACCESS, CONSOLE_REFRESH 쿠키
  5 <-- 302 /page/roles        이후 요청마다 쿠키의 access 를 검증
 1분 뒤
  6 GET /page/roles ---------> access 쿠키는 사라졌고 refresh 만 실린다
                                 refresh 로 재발급(회전), 새 쿠키 둘을 심고 그대로 화면
 로그아웃
  7 POST /page/logout -------> refresh 계보를 끊고(DB) 토큰 쿠키를 지운다
  8 <-- 302 /realms/master/logout?post_logout_redirect_uri=/
    ---------------------------------------------------------> 로그인 세션을 끝내고 AUTH_SESSION 삭제
  8 <-- 303 / ------------------------------------------------ 토큰이 없으니 다시 1번부터
```

## 왜 그렇게 도나

**운영 화면도 앱 하나다.** `auth-console` 이라는 MASTER 의 앱으로 등록돼 있고, 포털과 똑같이
로그인 서버에 로그인을 부탁한다. 같은 프로세스지만 남처럼 군다. 다른 점은 code 교환을 HTTP 로 하지
않고 유스케이스를 바로 부른다는 것 하나다. 검사(1회용, 돌아갈 주소, PKCE)는 같다.

**토큰을 쿠키에 둔다.** 서버 세션에 두면 인스턴스 메모리라, auth 를 여러 대 띄웠을 때 로그인을
시작한 곳과 돌아온 곳이 달라 깨진다. 쿠키에 두면 어느 인스턴스든 자기 공개키로 검증하면 된다.
auth 는 발급자 자신이라 discovery 나 JWKS 를 거치지 않고 메모리의 키로 본다.

**쿠키가 셋인 이유.** 경로가 다르다. 로그인 도중의 값(`CONSOLE_LOGIN`)은 콜백에서만 쓰니 경로를
`/page/login/callback` 으로 좁히고 10분 뒤 사라진다. 토큰 둘은 `/` 에 실린다. SSO 쿠키
`AUTH_SESSION` 은 로그인 서버 것이라 `/realms/master` 에만 실린다.

**로그아웃이 두 번 오가는 이유.** 운영 화면은 `AUTH_SESSION` 을 볼 수 없다(경로가 다르다). 자기
쿠키와 refresh 계보를 치운 뒤 로그인 서버의 로그아웃으로 넘겨서 거기서 SSO 세션을 끝낸다. refresh
계보는 운영 화면이 끊는다. 로그인 서버의 로그아웃은 앱이 든 refresh 를 받지 않는다.

**화면 요청만 로그인으로 보낸다.** 브라우저가 알아서 보내는 `/favicon.ico` 까지 로그인을 시작하면
`CONSOLE_LOGIN` 이 새 state 로 덮여 진행 중인 로그인이 400 으로 깨진다. `Accept` 에 `text/html`
이 없으면 쿠키를 건드리지 않고 401 이다.

**1분이 지나면 refresh 로 받는다.** access 쿠키는 토큰과 같이 1분 뒤 브라우저에서 사라지고 refresh
쿠키(24시간)는 남는다. 그 뒤에 오는 요청은 가드에서 재발급을 받아 그대로 통과한다. 로그인 서버를 돌지
않으니 폼을 내던 중에 만료돼도 입력이 사라지지 않는다. 재발급은 회전이라 낸 refresh 는 죽고 새 것이
쿠키에 들어간다. 재발급이 실패하면(로그아웃으로 끊긴 계보, 이미 쓴 토큰, 수명 끝) 토큰 쿠키를 지우고
1번부터 다시 돈다. `AUTH_SESSION` 이 살아 있으면 그때도 로그인 화면 없이 지나간다.

## 지키는 규칙

- 쿠키의 토큰을 믿지 않는다. 요청마다 서명, 발급자, 만료, `type=access` 를 본다
- `type` 을 빼지 않는다. refresh 도 같은 키로 서명돼 있어 빼면 24시간짜리가 access 자리를 통과한다
- state 는 한 번 쓰고 버린다. 맞지 않으면 교환하지 않는다(로그인 CSRF)
- 로그인 뒤 돌아갈 주소는 `/` 로 시작하고 `//` 로 시작하지 않을 때만 따른다
- 로그아웃은 POST 로만 받는다. GET 이면 이미지 태그 하나로 로그아웃시킬 수 있다
- 로그아웃과 콜백은 가드에서 뺀다. access 가 만료된 뒤에도 끝까지 가야 한다
- 재발급이 실패하면 토큰 쿠키를 지운다. 남겨 두면 요청마다 같은 실패를 되풀이한다
- 새 엔드포인트를 `/realms`, `/api`, `/.well-known` 밖에 두면 로그인 뒤로 들어간다
- 돌아갈 주소는 `token.issuer` 에서 만든다. 두 군데 적으면 포트를 옮길 때 한쪽만 고친다

## 아직 없는 것

- **동시 재발급.** 탭 둘이 같은 순간에 만료된 채로 요청하면 둘 다 같은 refresh 로 재발급하고, 진 쪽이
  "이미 쓴 토큰" 으로 보여 계보가 끊긴다. SSO 세션이 살아 있어 로그인 화면 없이 다시 받지만, 그 사이
  폼을 내던 쪽은 입력을 잃는다
- **권한 검사.** MASTER 에 계정만 있으면 들어온다. 그래서 운영 화면은 아직 `local` 에서만 뜬다
- **MASTER 관리자의 권한.** MASTER 의 역할 `ADMIN` 에 권한이 하나도 붙어 있지 않다. 관리
  API(`/api/admin/**`)는 여전히 호출자를 ADMIN realm 으로 못박고 있어서 MASTER 토큰으로는 못 부른다
- **돌아갈 주소 목록 분리.** 로그인과 로그아웃이 같은 목록을 본다. 로그아웃용으로 등록한 `/` 로
  로그인 code 를 받는 것도 허용된다. Keycloak 은 둘을 따로 둔다
- **CSRF 토큰.** 쿠키 인증이라 `SameSite=Lax` 에 기댄다. 폼마다 토큰을 두지는 않는다
- **여러 대에서의 안내 문구.** 화면의 "만들었다" 같은 문구는 아직 서버 세션(flash)을 쓴다.
  여러 대면 이 문구만 가끔 사라진다
- **공용 검증기의 type 검사.** `AccessTokenReader.read()` 는 type 을 보지 않는다. 운영 화면은 따로
  보지만, `read()` 를 쓰는 다른 경로는 refresh 를 access 로 받을 수 있다
