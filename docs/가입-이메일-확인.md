# 가입 이메일 확인

가입할 때 그 이메일의 주인인지 확인하는 과정. 번호를 보내고, 받고, 확인하고, 쓰는 걸음마다 규칙이
붙어 있어서 따로 적는다. 가입 전체의 모양은 [회원가입](회원가입.md)에 있다.

## 왜 확인하나

| 확인하지 않으면 | 무엇이 문제인가 |
|---|---|
| 남의 주소로 계정을 만들 수 있다 | 진짜 주인이 나중에 오면 그 주소는 이미 남의 계정이다 |
| 미확인 계정이 쌓인다 | 그 사람이 구글로 들어올 때 자동 연결이 막힌다(pre-account hijacking 방어) |
| 가입 폼으로 "이 주소가 가입돼 있나" 를 물을 수 있다 | 주소를 넣어보는 것만으로 회원을 훑는다 |

그래서 비밀번호로 가입해도 번호를 먼저 받는다. 가입으로 생긴 이메일 계정은 언제나 확인된 주소다.

## 한눈에

1단계는 번호를 보내기만 한다. 아무것도 만들지 않는다.

```
1단계 요청: POST /auth/register/send-code 또는 /register/send-code   email, name, phoneNumber

1. 인가 요청 검증           등록된 앱, 등록된 주소인가. 가입만 하는 입구는 없다  (컨트롤러)
2. 입력 확인                이메일 모양, 이름이 비었나                 (컨트롤러)
3. 이 realm 에 가입된 주소  맞으면 보내지 않고 조용히 끝                (RequestRegistrationOtpService)
4. 60초 안에 보낸 번호      있으면 보내지 않고 조용히 끝                (EmailOtpIssuer)
5. 번호 만들기              6자리. 해시만 저장, 5분                    (EmailOtpIssuer)
                            메일 발송. local 은 안 보내고 123456
6. 번호 칸이 열린 화면      보냈든 안 보냈든 같은 화면
```

가입은 사용자 정보가 들어오는 2단계 요청 하나 안에서 일어난다. 이메일과 번호를 먼저 확인하고,
통과해야만 신원을 만든다.

```
2단계 요청: POST /auth/register 또는 /register   email, name, phoneNumber, code, password(선택)
           + 인가 요청 값 (가입만 하는 입구는 client_id, redirect_uri 만)

1. 인가 요청 검증           등록된 앱, 등록된 주소인가. 가입만 하는 입구는 없다  (컨트롤러)
2. 입력 확인                이메일 모양, 이름이 비었나                 (컨트롤러)
3. 비밀번호 길이            적었을 때만. 8~64자                        (컨트롤러)
   ── 여기부터 한 트랜잭션 ──
4. 이메일 + 번호 대조       이 요청의 email 앞으로 저장된 최신 번호와  (EmailOtpVerifier)
                            이미 5번 틀렸나 / 만료됐나 / 맞나
                            틀리면 시도 +1 을 따로 커밋하고 끝. 아무것도 안 만든다
                            맞으면 사용 처리
5. 이미 가입된 주소인가     비밀번호를 적었으면 거절                   (가입 서비스)
                            비웠으면 새로 만들지 않고 그 계정으로 로그인
6. 가입                     신원 채번, 프로필(이름, 전화), 이메일(확인됨),
                            비밀번호 계정(적었을 때), "생겼다" 이벤트 -> 기본 역할
   ── 트랜잭션 끝 ──
7. 입구에 따라 끝이 갈린다
   /auth/register (prompt=create)   로그인 확정(인증 시각, 인증 이벤트), 세션 쿠키, code 를 앱 주소로 303
   /register (가입만)               "가입을 완료했습니다" 화면. 등록된 돌아갈 주소면 하단에 링크
```

4번이 6번보다 앞에 있고 둘이 같은 트랜잭션이라는 것이 요점이다. 4번에서 틀리면 이름, 전화번호,
비밀번호는 쓰이지 않고 버려진다. 6번이나 이벤트 쪽에서 실패하면 4번의 사용 처리까지 함께 되돌아가서,
사람은 같은 번호로 다시 시도할 수 있다.

## 왜 그렇게 도나

**1단계는 늘 같은 화면이다.** 가입된 주소라서 안 보냈든, 60초 안이라 안 보냈든, 보냈든 화면이 같다.
갈라 보여주면 주소를 넣어보는 것만으로 누가 가입했는지 알 수 있다. 가입된 주소면 번호가 나가지
않으므로, 그 사람은 2단계에서 "번호가 맞지 않다" 는 말만 보게 된다.

**"확인됐다" 는 상태를 들고 다니지 않는다.** 1단계는 번호를 그 이메일 앞으로 저장하고 끝난다. 2단계는
요청에 적혀 온 이메일로 번호를 찾아 대조한다. 확인과 가입이 같은 요청 안에서 같은 이메일로 일어난다.
그래서 2단계에서 이메일 칸을 고쳐 보내도 가입되지 않는다(`readonly` 는 화면의 장식일 뿐이다).

```
1단계  A 로 번호 요청         A 메일함으로 번호가 간다
2단계  email=B, code=A의 번호  서버는 B 앞으로 저장된 번호와 대조한다 -> 맞지 않는다
```

B 로 가입하려면 B 앞으로 발급된 번호를 알아야 하고, 그 번호는 B 의 메일함으로만 간다. 1단계에서
"A 확인 완료" 를 세션에 두고 2단계가 그 표시만 믿었다면, 이메일을 바꿔 보내는 것만으로 남의 주소가
확인된 계정이 생겼을 것이다. 이름과 전화번호도 hidden 으로 오가지만 원래 사람이 적는 값이라 고쳐도
잃는 것이 없다.

**비밀번호는 2단계에서 받는다.** 1단계에서 받으면 번호 화면까지 hidden 값으로 들고 다녀야 한다. 길이
검사는 번호를 확인하기 전에 한다. 번호는 확인하는 순간 쓰인 것이 되므로, 비밀번호 때문에 되돌려
보낼 일이면 번호를 쓰기 전에 걸러야 사람이 번호를 다시 받지 않는다.

**번호 확인이 가입 여부 확인보다 먼저다.** 순서가 반대면 주소 주인이 아니어도 "이미 가입된 이메일" 이라는
답을 볼 수 있다. 번호를 통과했다는 것은 그 메일함을 연 사람이라는 뜻이라, 그 뒤에는 알려줘도 된다.

**번호 소모와 가입은 한 트랜잭션이다.** 가입이 어디서든 실패하면(가입된 주소, 기본 역할 부여 실패)
번호의 사용 처리도 함께 되돌아간다. 사람은 5분 안이면 같은 번호로 다시 시도할 수 있다. 반대로 틀린
횟수는 되돌아가면 안 된다. 되돌아가면 5회 제한이 영원히 걸리지 않는다. 그래서 실패 기록만 별도
트랜잭션(`REQUIRES_NEW`)으로 커밋한다.

**가입된 주소의 번호를 들고 와도 끝이 둘로 갈린다.** 가입용 번호는 가입된 주소로 나가지 않지만, 로그인용
번호는 나간다. 그 번호를 가입 폼에 적으면 이렇게 된다.

| 2단계에서 | 결과 | 이유 |
|---|---|---|
| 비밀번호를 비웠다 | 새로 만들지 않고 그 계정으로 로그인 | 주인임을 방금 증명했다. 알려줄 새 정보가 없다 |
| 비밀번호를 적었다 | "이미 가입된 이메일" 로 거절 | 기존 신원에 비밀번호를 붙이는 일은 로그인한 뒤에 한다 |

## 경우별로

| 경우 | 화면 | 번호 |
|---|---|---|
| 정상 | 303, 로그인된 채로 앱으로 | 사용됨 |
| 번호가 틀림 | 401, 번호 칸 그대로 "일치하지 않습니다" | 시도 +1 |
| 5번 틀린 뒤 | 401 "시도 횟수를 초과했습니다". 맞는 번호도 받지 않는다 | 막힘. 새 번호를 받아야 함 |
| 5분 지남 | 401 "만료되었습니다" | 새 번호를 받아야 함 |
| 번호를 안 받았거나 다 씀 | 401 "유효하지 않습니다" | - |
| 60초 안에 다시 요청 | 같은 화면. 새로 보내지 않음 | 앞의 번호가 그대로 유효 |
| 비밀번호가 8자 미만, 64자 초과 | 401, 번호 칸 그대로 | 쓰이지 않음 |
| 번호 받은 사이 가입됨 + 비밀번호 | 401 "이미 가입된 이메일" | 되돌아가 쓰이지 않음 |

## 지키는 규칙

- **번호 원문은 저장하지 않는다.** 해시만 둔다. 표가 새도 유효한 번호가 함께 새지 않는다
- **확인하는 번호는 그 주소의 최신 미사용 번호 하나.** 새 번호를 받으면 앞의 번호는 볼 일이 없다
- **실패 기록은 따로 커밋, 사용 처리는 가입과 함께.** 둘을 바꾸면 잠금이 안 걸리거나 번호가 헛돈다
- **1단계 응답은 가입 여부와 쿨다운을 가르지 않는다**
- **가입 여부는 번호를 통과한 뒤에만 말한다**
- **번호는 요청에 적힌 이메일로 찾는다.** 1단계의 결과를 세션이나 hidden 값으로 믿지 않는다
- **로컬은 메일을 보내지 않고 `123456` 을 쓴다.** 운영에서 메일 어댑터가 없으면 발송 단계에서 멈춘다

## 아직 없는 것

- **번호 찍어 보기를 막는 장치가 약하다.** 번호 하나에 5번이라 한 번호로 맞힐 확률은 100만분의 5지만,
  60초마다 새 번호를 받을 수 있어 하루 내내 시도하면 약 7,200번이 되고 확률은 0.7% 남짓까지 오른다. 그동안
  그 주소의 주인은 번호 메일을 1,400통 넘게 받는다. 이메일당 하루 발송 상한, IP 당 요청 제한, 캡차가 없다

- **번호가 용도와 realm 을 가리지 않는다.** 표에 이메일만 있다. 로그인용 번호로 가입하고, 한 realm 에서 받은
  번호를 다른 realm 에 낼 수 있다. 어느 쪽이든 그 메일함의 주인이라 지금은 구멍이 아니지만, 쿨다운도
  용도를 가리지 않아 로그인 번호를 받은 직후 60초는 가입 번호를 받을 수 없다
- **쓰이지 않은 번호 치우기.** 만료된 행이 그대로 남는다
- **메일 발송 어댑터.** 운영용 구현이 없다. local 밖에서는 발송 단계에서 멈춘다
- **보낸 곳 숨기기.** 화면이 "○○ 로 보냈습니다" 라고 적은 주소를 그대로 보여준다. 보냈는지는 가르지 않지만
  주소를 되읽어 주는 것은 남아 있다
