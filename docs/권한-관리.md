# 권한 관리

누가 무엇을 할 수 있는지 정하는 곳. 신원(누구인가)과는 다른 물음이다.

## 세 층으로 나눈다

```
사람  --(맡은 일)-->  역할  --(할 수 있는 일)-->  권한  --(여는 문)-->  URL 규칙

      authz_subject_role   authz_role         authz_permission   각 서비스의 코드
```

한 층씩 이유가 있다.

**역할에는 서비스 구분이 없다.** 역할은 "이 사람이 조직에서 맡은 일"(관리자, 상담원, 고객)이고
그것은 서비스마다 달라지지 않는다. 한 역할이 여러 서비스의 권한을 가질 수 있다.

**권한은 서비스로 갈린다.** 어휘가 전역이면 부딪힌다. `order-service` 의 `READ` 와
`customer-service` 의 `READ` 는 다른 것이다. 서비스로 가르면 그 충돌이 구조적으로 불가능해진다.

**URL 규칙은 각 서비스가 자기 코드로 갖는다.** "이 권한이 어떤 문을 여는가" 는 그 서비스의
사정이라 그 서비스와 함께 배포된다(`SecurityConfiguration` 이나 `@PreAuthorize`). auth 는 권한의
이름만 보관한다. 2026-09-29 에 이렇게 정했다. URL 규칙을 auth 의 표에 두고 화면에서 고치는 방식도
있었지만, 서비스가 여럿이면 그 규칙을 서비스마다 나눠 주는 장치가 따로 필요하고, URL 과 권한의
연결은 어차피 엔드포인트를 만들 때 코드와 함께 바뀐다.

## 사람에게는 역할만 준다

권한을 사람에게 직접 주지 않는다. 그러면 "이 사람이 왜 이걸 할 수 있지" 를 물었을 때 답이
개인마다 흩어지고, 조직이 바뀔 때 한 명씩 고쳐야 한다. 역할을 거치면 답이 하나다.
**그 사람이 맡은 일이 그것이기 때문이다.**

## 데이터는 auth 에, 판정은 각 서비스에

```
auth                                      토큰 (access)                         서비스
────                                      ─────────────                         ──────
사람 -> 역할 -> 권한  ── 발급할 때마다 ──>  realm_access.roles                    (읽지 않는다)
                         다시 읽는다       resource_access.order-service.roles ─> order-service 가 자기 칸만
                                           resource_access.customer-service... ─> customer-service 가 자기 칸만
                                                                                  (URL, 메서드) -> 필요한 권한
                                                                                  규칙이 없는 경로는 거부
```

**auth 는 누가 무엇을 가졌는지 안다.** 토큰을 발급할 때(로그인, 재발급 모두) 그 사람의 역할과,
역할을 거쳐 얻은 권한을 서비스별로 묶어 싣는다. Keycloak 의 realm role 과 client role 자리다.

**서비스는 자기 칸만 읽고, 권한으로 판정한다.** order-service 는 `ORDER_READ`, `ORDER_WRITE` 를,
customer-service 는 `PROFILE_READ`, `PROFILE_WRITE` 를 경로마다 요구한다(`hasAuthority`). 역할은 보지
않는다. 역할은 조직의 언어라 서비스 코드에 넣으면 조직이 바뀔 때 서비스를 고쳐야 한다. 권한으로
판정하면 "상담원도 주문을 넣게" 같은 변경은 auth 에서 역할-권한 연결만 바꾸면 끝난다.

**역할은 토큰에 남는다.** 서비스 판정에는 쓰지 않지만 화면 분기(관리자 메뉴를 보일까)나 게이트웨이의
거친 검사에 쓸 수 있다.

**늦어도 access 수명(1분)만큼이다.** 권한을 바꾸면 다음 발급부터 실린다. 이미 나간 access 토큰은
만료될 때까지 옛 권한을 들고 다니고, 재발급하는 순간 새 권한으로 바뀐다.

**고치는 화면은 [권한 관리 화면](권한-관리-화면.md) 에 있다.** 역할에 권한을 묶고 사람에게 역할을 붙인다.

**auth 콘솔 자신은 다르다.** auth 의 관리 API 는 토큰이 아니라 요청마다 DB 를 읽어 `AUTHZ_MANAGE` 를
본다. 그 권한은 서비스가 없는 권한이라 토큰에도 실리지 않는다. 자세한 것은 [토큰 흐름](토큰-흐름.md).

**서비스가 늘면 토큰이 커진다.** 같은 시스템(`aud`) 아래 서비스마다 칸이 하나씩 늘어난다. 한계와
대안은 [MSA 인가 방식](MSA-인가-방식.md) 에 있다.

**auth 에 남은 것.** URL 규칙 표(`authz_url_access`, `authz_url_permission`)와 그 관리 API, 규칙을
realm 별로 캐시하고 TTL(기본 60초)로 다시 읽는 판정 엔진(`AccessControlService`)이 있다. 서비스가
auth 에 판정을 맡기던 구성의 흔적이다. 정리할지는 정하지 않았다.

## 지키는 규칙

- **권한은 역할을 통해서만 준다**
- **서비스는 권한으로 판정한다.** 역할 이름(`hasRole`)을 서비스 코드에 넣지 않는다
- **서비스는 자기 칸만 읽는다.** 남의 서비스 칸까지 읽으면 이름이 같은 권한이 생기는 날 남의 문이 열린다
- **식별자는 바뀌지 않는다.** `roleCode`, `permissionCode` 가 바뀌면 그것은 수정이 아니라 다른
  역할, 다른 권한이다. 이미 그 코드에 기대던 URL 규칙과의 대응이 끊긴다
- **지우는 대신 끈다.** `use_yn` 으로 내린다. 지우면 무엇이 있었는지가 사라진다
- **없는 서비스의 권한은 만들 수 없다.** 외래키가 붙든다. 오타가 조용히 지나가면 그 권한은
  토큰에 실릴 곳이 없다
- **관리 API 는 MASTER realm 토큰 + `AUTHZ_MANAGE`.** auth 를 관리하는 것은 MASTER 다. 직원 realm 은 업무
  시스템을 쓰는 사람들의 자리다. 경로의 realm 은 호출자가 아니라 **편집 대상**이다

## 어디에 있나

| 무엇 | 어디 |
|---|---|
| 토큰에 실을 역할과 서비스별 권한 조회 | `auth-application/.../authorization/service/SubjectAuthorityService.java` |
| 역할-권한을 잇는 쿼리 | `auth-dataaccess/.../authorization/repository/AuthzSubjectRoleJpaRepository.java` |
| 토큰에 싣는 자리 | `auth-application/.../identity/service/TokenIssuance.java`, `.../identity/token/RbacJwtTokenIssuer.java` |
| 서비스가 자기 칸을 읽는 변환기 | `order-service/.../web/support/ServicePermissionAuthorities.java` (customer-service 에도 같은 것) |
| 서비스의 URL 규칙 | 각 서비스의 `web/support/SecurityConfiguration.java` |
| 판정 엔진, 캐시, TTL (부르는 곳 없음) | `auth-application/.../authorization/service/AccessControlService.java` |
| 역할 | `auth-domain/.../domain/authorization/Role.java` |
| 권한 | `auth-domain/.../domain/authorization/Permission.java` |
| URL 규칙 | `auth-domain/.../domain/authorization/UrlRule.java` |
| 관리 API | `auth-web/.../web/admin/authorization/` |
| 역할 화면(목록, 추가, 역할의 권한 편집) | `auth-web/.../web/admin/console/RoleConsoleController.java` |
| 사람의 역할 화면 | `auth-web/.../web/admin/console/SubjectConsoleController.java` |
| 권한 화면(보기만) | `auth-web/.../web/admin/console/PermissionConsoleController.java` |
| 표 | `authz_service`, `authz_role`, `authz_permission`, `authz_url_access`, `authz_subject_role` (V2) |

## 아직 없는 것

- **쓰이지 않는 판정 엔진과 URL 규칙 표의 정리**
- **서비스가 많아졌을 때의 토큰 크기 대책.** [MSA 인가 방식](MSA-인가-방식.md) 에 제안만 있다
- **역할 계층.** 역할이 역할을 포함하는 구조가 없다
- **그룹.** 사람을 묶어 한꺼번에 역할을 주는 단위가 없다
