# 권한 관리

누가 무엇을 할 수 있는지 정하는 곳. 신원(누구인가)과는 다른 물음이다.

## 세 층으로 나눈다

```
사람  --(맡은 일)-->  역할  --(할 수 있는 일)-->  권한  --(여는 문)-->  URL 규칙

      authz_subject_role   authz_role         authz_permission   각 서비스의 코드
```

한 층씩 이유가 있다.

**역할에는 서비스 구분이 없다.** 역할은 "이 사람이 조직에서 맡은 일"(관리자, 상담원, 고객)이고
그것은 서비스마다 달라지지 않는다. 한 역할이 여러 서비스의 권한을 가질 수 있다.

**권한은 서비스로 갈린다.** 어휘가 전역이면 부딪힌다. `order-service` 의 `READ` 와
`customer-service` 의 `READ` 는 다른 것이다. 서비스로 가르면 그 충돌이 구조적으로 불가능해진다.

**URL 규칙은 각 서비스가 자기 코드로 갖는다.** "이 권한이 어떤 문을 여는가" 는 그 서비스의
사정이라 그 서비스와 함께 배포된다(`SecurityConfiguration` 이나 `@PreAuthorize`). auth 는 권한의
이름만 보관한다. 2026-09-29 에 이렇게 정했다. URL 규칙을 auth 의 표에 두고 화면에서 고치는 방식도
있었지만, 서비스가 여럿이면 그 규칙을 서비스마다 나눠 주는 장치가 따로 필요하고, URL 과 권한의
연결은 어차피 엔드포인트를 만들 때 코드와 함께 바뀐다.

## 사람에게는 역할만 준다

권한을 사람에게 직접 주지 않는다. 그러면 "이 사람이 왜 이걸 할 수 있지" 를 물었을 때 답이
개인마다 흩어지고, 조직이 바뀔 때 한 명씩 고쳐야 한다. 역할을 거치면 답이 하나다.
**그 사람이 맡은 일이 그것이기 때문이다.**

## 판정은 어디서 하나

정한 모양은 이렇다.

```
요청 --> 그 서비스가 자기 코드의 규칙으로 (URL, 메서드) 에 필요한 권한을 안다
         호출자가 그 권한을 가졌나
         규칙이 없는 경로는 거부                       <- 화이트리스트
```

**지금은 거기까지 가 있지 않다.** customer-service, order-service 는 로그인 여부만 본다
(`anyRequest().authenticated()`). 서비스가 호출자의 권한을 알아낼 길(토큰에 다시 싣거나 auth 에
묻거나)을 아직 정하지 않았기 때문이다.

**auth 에 남은 것.** URL 규칙 표(`authz_url_access`, `authz_url_permission`)와 그 관리 API, 규칙을
realm 별로 캐시하고 TTL(기본 60초)로 다시 읽는 판정 엔진(`AccessControlService`)이 있다. 서비스가
auth 에 판정을 맡기는 구성의 흔적이고, 지금은 부르는 곳이 없다. 지울지는 정하지 않았다.

## 토큰에는 권한이 없다

토큰은 "이 요청이 누구인가" 만 답한다. 역할도 권한도 싣지 않는다. 한때 실었는데, 그러면 같은
판단이 세 군데(토큰 클레임, auth 의 표, 소비 서비스의 매처)에 나뉘고 **권한을 바꿔도 이미 발급된
토큰은 옛 권한을 들고 다닌다.**

지금은 권한을 물어보는 시점이 판정 시점이다. 자세한 것은 [토큰 흐름](토큰-흐름.md).

## 지키는 규칙

- **권한은 역할을 통해서만 준다**
- **식별자는 바뀌지 않는다.** `roleCode`, `permissionCode` 가 바뀌면 그것은 수정이 아니라 다른
  역할, 다른 권한이다. 이미 그 코드에 기대던 URL 규칙과의 대응이 끊긴다
- **지우는 대신 끈다.** `use_yn` 으로 내린다. 지우면 무엇이 있었는지가 사라진다
- **없는 서비스의 권한은 만들 수 없다.** 외래키가 붙든다. 오타가 조용히 지나가면 그 권한은
  토큰에 실릴 곳이 없다
- **관리 API 는 MASTER realm 토큰 + `AUTHZ_MANAGE`.** auth 를 관리하는 것은 MASTER 다. 직원 realm 은 업무
  시스템을 쓰는 사람들의 자리다. 경로의 realm 은 호출자가 아니라 **편집 대상**이다

## 어디에 있나

| 무엇 | 어디 |
|---|---|
| 판정 엔진, 캐시, TTL (부르는 곳 없음) | `auth-application/.../authorization/service/AccessControlService.java` |
| 역할 | `auth-domain/.../domain/authorization/Role.java` |
| 권한 | `auth-domain/.../domain/authorization/Permission.java` |
| URL 규칙 | `auth-domain/.../domain/authorization/UrlRule.java` |
| 관리 API | `auth-web/.../web/admin/authorization/` |
| 관리 화면 | `frontends/backoffice/src/pages/RbacPage.jsx` |
| 역할 운영 화면(auth, 목록과 추가) | `auth-web/.../web/admin/console/RoleConsoleController.java` |
| 표 | `authz_service`, `authz_role`, `authz_permission`, `authz_url_access`, `authz_subject_role` (V2) |

## 아직 없는 것

- **서비스가 권한을 아는 길.** URL 규칙은 서비스 코드에 두기로 했지만, 그 규칙이 물을 "호출자의
  권한" 을 서비스가 얻는 길이 없다. 토큰에 다시 싣거나 auth 에 묻거나 둘 중 하나다
- **서비스의 URL 규칙.** 그래서 지금 서비스들은 로그인만 보고 권한은 보지 않는다
- **쓰이지 않는 판정 엔진과 URL 규칙 표의 정리**
- **역할 계층.** 역할이 역할을 포함하는 구조가 없다
- **그룹.** 사람을 묶어 한꺼번에 역할을 주는 단위가 없다
