# 모듈 구조

auth-service 가 여덟 모듈로 갈려 있는 이유와, 그 안에서 코드가 어느 자리에 가는지.

## 왜 나누나

한 모듈에 다 두면 규칙이 규율로만 선다. "도메인은 JPA 를 몰라야 한다" 를 아무리 적어둬도,
`import jakarta.persistence` 한 줄이면 그 규칙은 조용히 깨진다.

**모듈로 나누면 컴파일이 막는다.** 도메인 모듈에 JPA 의존성이 아예 없으니 그 import 를 쓸 수가
없다. 문서 대신 빌드가 규칙을 지킨다.

## 여덟 모듈

```
auth-domain        순수 도메인. Spring 도 JPA 도 모른다
auth-application   유스케이스. 들어오는 구멍(port.in)과 나가는 구멍(port.out)
                   ┌──────────────── 밖으로 나가는 길은 성격별로 하나씩 ────────────────┐
auth-dataaccess    DB            auth-messaging  이벤트        auth-external  외부 API
                   └──────────────────────────────────────────────────────────────────┘
auth-web           들어오는 길. 컨트롤러와 화면
auth-client        다른 서비스가 토큰을 검증할 때 쓰는 라이브러리
auth-bootstrap     실행. 이것들을 한 프로세스로 묶는다
```

의존은 **안쪽으로만** 흐른다. `web -> application -> domain`. 어댑터들은 application 이 선언한
포트를 구현할 뿐이고, application 은 그 구현이 누구인지 모른다.

`auth-bootstrap` 만 모두를 의존한다. 코드는 `@SpringBootApplication` 하나와 설정뿐이다. 로직이
여기 들어오면 계층 경계가 무너진다.

## auth-client 가 따로 있는 이유

소비 서비스(customer-service 등)가 토큰을 검증할 때 쓰는 라이브러리다. **auth 의 레이어 모듈을
하나도 의존하지 않는다.**

남의 서비스가 우리 도메인 모델을 알게 되면, auth 의 내부 변경이 그쪽 컴파일을 깨뜨린다.
주고받는 것은 토큰 문자열과 그 안의 클레임뿐이고, 그것이 이 경계의 계약이다.

## 코드가 어느 자리에 가나

새 기능을 만들 때 매번 부딪히는 질문이라 기준을 적어 둔다.

| 이런 것 | 어디 |
|---|---|
| "코드는 1분 산다", "주소는 글자 그대로 대조한다" | `domain` |
| "이 이름이 이미 쓰이고 있나"(저장소를 봐야 안다) | `application` |
| "쿠키를 심는다", "303 으로 돌려보낸다" | `web` |
| "이 표의 이 칸에 적는다" | `dataaccess` |

**시각도 도메인이 정하지 않는다.** `AuthorizationCode.issue(..., Instant now)` 처럼 밖에서
받는다. 도메인이 `Instant.now()` 를 부르면 "1분 뒤에 죽는다" 를 시계를 돌리지 않고는 확인할 수
없다.

## web 은 채널로 갈린다

패키지의 첫 세그먼트가 **"누가 부르는가"** 다. 서브도메인(identity/authorization)이 아니다.

```
web/admin       운영자. /api/admin/** 과 운영 화면
web/authorize   로그인하는 사람의 브라우저. 화면과 리다이렉트
web/broker      구글이 돌려보낸 브라우저
web/wellknown   다른 서비스. 공개 메타데이터
```

채널이 축인 이유는, MSA 로 갈 때 갈라지는 선이 그것이기 때문이다. 게이트웨이 라우팅, 네트워크
구역, 레이트 리밋, 결국 배포 단위가 채널을 따라 나뉜다. 서브도메인을 따라 나뉘지 않는다.

각 채널 패키지에 `package-info.java` 가 있고 거기 그 채널의 규칙이 적혀 있다. 새 엔드포인트가
그 규칙 중 하나라도 어기면 그것은 다른 채널의 것이다.

## 테스트가 계층을 따라간다

```
domain        순수 단위 테스트. 스프링도 DB 도 없다
application   가짜 포트 구현으로 유스케이스만 본다
dataaccess    Testcontainers 로 실제 PostgreSQL. 마이그레이션 스키마 위에서 돈다
```

**영속성 테스트가 실제 DB 를 쓰는 것**이 중요하다. 엔티티에서 스키마를 만들면(ddl-auto) 테스트가
통과해도 운영 스키마에서 도는지는 알 수 없다. 지금은 Flyway 가 만든 스키마 위에서 돌고,
엔티티가 그와 어긋나면 테스트가 뜨지도 않는다.

가짜 포트로 잡히지 않는 것도 있다. 트랜잭션 경계가 그렇다. 인가 코드가 교환에 실패해도 태워져야
한다는 규칙은 가짜 저장소에서는 통과하고 실제 DB 에서 깨졌다.

## 아직 없는 것

- **모듈 간 의존 검사.** 지금은 pom 의 의존 선언이 규칙을 지킨다. ArchUnit 같은 것으로 패키지
  단위 규칙(채널 규칙 등)까지 못 박을 수 있다
- **auth-client 를 쓰는 서비스.** 이 저장소에 소비 서비스가 함께 있지만, 라이브러리로 배포해
  쓰는 형태는 아직 아니다
