# 비밀번호 로그인

auth 의 로그인 화면에서 아이디와 비밀번호로 사람을 확인하는 길. 앱은 비밀번호를 보지 않는다.

## 왜 이렇게 하나

전에는 앱이 비밀번호를 받아 `/api/auth/realms/{realm}/login` 에 내밀고 그 자리에서 토큰을 받았다.
OAuth 가 ROPC 라고 부르는 방식이고, 지금은 쓰지 말라고 하는 쪽이다. 그 API 는 지웠다.

| | 전 (ROPC) | 지금 |
|---|---|---|
| 비밀번호를 받는 쪽 | 앱 | auth 의 로그인 화면 |
| 확인이 끝나고 나가는 것 | 토큰 | 로그인 세션과 code 한 장 |
| 토큰이 나가는 때 | 확인한 그 자리 | 앱이 code 를 바꿀 때 |
| 2단계 인증, 약관 동의 | 넣을 자리가 없다 | auth 화면에서 바꾼다 |

## 한눈에

```
  브라우저                         auth                          DB
   |                                |                            |
   |-- POST /realms/{realm}/auth/login                           |
   |   loginId, password,           | 인가 요청 다시 검증           |
   |   인가 요청(hidden)             | (realm, login_id) 로 조회 --->| identity_password_account
   |                                | 잠겼나, 해시 비교              |
   |                                | 실패 카운트 정리               |
   |                                | 신원 조회, realm 대조          |
   |                                | 인증 시각 기록, 이벤트         |
   |<- 303 redirect_uri?code=&state=| 세션 쿠키 심기, code 발급      |
```

그 뒤는 [인가 코드 흐름](인가-코드-흐름.md)과 같다. 앱이 code 를 토큰으로 바꾼다.

## 왜 그렇게 도나

**인증과 발급이 갈려 있다.** `EstablishPasswordAuthenticationUseCase.withPassword()` 는 "누가
로그인했나" 까지만 확정하고 멈춘다. 토큰은 앱이 code 를 바꾸러 올 때 그 사람 앞으로 나간다.
인증 시각과 인증 이벤트는 사람이 비밀번호를 적은 때에 남는다.

**틀리면 앱에 알리지 않는다.** 로그인 화면을 오류 문구와 함께 다시 그린다(401). 돌아갈 주소로
실패를 보내지 않는다.

**인가 요청을 폼마다 다시 검증한다.** 화면의 hidden 값으로 오가서 브라우저에서 고칠 수 있다.
등록된 앱과 주소, PKCE 가 맞지 않으면 우리 오류 화면에서 끝난다.

## 실패를 한 가지로 만든다

없는 아이디와 틀린 비밀번호가 같은 문구로 끝난다. 다르게 답하면 아이디만 바꿔가며 넣어보는
것으로 누가 가입돼 있는지 훑을 수 있다. 잠금만 예외다. 잠겼다는 사실은 알려준다. 모르면 사람이
계속 시도하고 그 시도가 잠금을 연장한다.

## 연속 실패를 잠근다

```
5회 연속 실패  ->  10분 잠금
잠긴 동안은 비밀번호를 비교하지도 않는다
성공하면 카운트와 잠금을 푼다
```

해시 비교는 일부러 느린 연산이라, 잠긴 동안 비교를 건너뛰는 것이 부하도 막는다. 실패 기록은
독립 트랜잭션에서 커밋된다(`REQUIRES_NEW`). 실패는 예외로 끝나고 그 예외가 트랜잭션을 되돌리는데,
실패 횟수까지 되돌아가면 잠금은 영원히 걸리지 않는다.

## 지키는 규칙

- **비밀번호는 앱을 거치지 않는다.** 받는 곳은 auth 의 로그인 화면 하나다
- **이 폼은 토큰을 내주지 않는다.** 세션과 code 까지다
- **조회는 realm 으로 좁힌다.** 상대 realm 에 같은 아이디가 있어도 걸리지 않는다
- **자격증명의 realm 과 신원의 realm 을 한 번 더 대조한다.** 어긋나면 데이터가 깨진 것이다
- **비밀번호는 BCrypt 해시로만 저장한다.** 원문은 어디에도 남지 않는다
- **실패 문구는 하나.** 잠금만 예외다

## 어디에 있나

| 무엇 | 어디 |
|---|---|
| 로그인 화면 | `auth-web/src/main/resources/templates/oauth/login.html` |
| 폼 제출, 세션, code | `auth-web/.../web/authorize/LoginSubmissionController.java` |
| 인증까지만 하는 포트 | `auth-application/.../identity/ports/in/EstablishPasswordAuthenticationUseCase.java` |
| 흐름 | `auth-application/.../identity/service/AuthenticateWithPasswordService.java` |
| 해시 비교, 잠금 | `auth-application/.../identity/service/PasswordCredentialVerifier.java` |
| 잠금 규칙 | `auth-domain/.../domain/identity/PasswordAccount.java` |
| 인증 확정(시각, 이벤트) | `auth-application/.../identity/service/AuthenticationCompletion.java` |
| 실패 기록(독립 트랜잭션) | `auth-dataaccess/.../identity/adapter/PasswordAccountPersistenceAdapter.java` |
| 표 | `identity_password_account` (V1) |

비밀번호 계정은 가입 화면에서 생긴다. [회원가입](회원가입.md)을 본다. 직원 realm 에는 비밀번호
계정이 없어서, 직원이 이 폼을 쓰면 늘 같은 실패 문구로 끝난다.

## 아직 없는 것

- **2단계 인증.** 이제 넣을 자리(auth 화면)는 있지만 만들지 않았다
- **비밀번호 변경과 재설정.** 계정을 만든 뒤 바꿀 길이 없다
- **이미 있는 신원에 비밀번호 붙이기.** 구글이나 인증번호로 가입한 사람은 비밀번호를 가질 수 없다.
  로그인한 뒤 설정하는 화면이 필요하다
- **비밀번호 정책.** 길이(8자 이상 64자 이하)만 본다. 유출된 비밀번호 목록 대조 같은 것은 없다
- **잠금 해제.** 10분을 기다리는 것 말고 운영자가 푸는 길이 없다
