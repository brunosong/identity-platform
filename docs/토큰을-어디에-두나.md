# 토큰을 어디에 두나

토큰 둘 다 **응답 본문으로 나가고 앱이 든다.** 쿠키는 쓰지 않는다.

| | 어디로 가나 | 어떻게 실리나 | 앱이 두는 자리 |
|---|---|---|---|
| access | customer-service, order-service, ... | `Authorization: Bearer` | 메모리 |
| refresh | 토큰 엔드포인트 하나뿐 | 폼 본문 `refresh_token=` | 메모리 |

```
POST /realms/portal/token
  grant_type=authorization_code&code=...&code_verifier=...

  {"access_token":"...","refresh_token":"...","token_type":"Bearer"}
```

재발급도 **같은 주소**다. `grant_type` 이 무엇을 하는 요청인지 가른다(RFC 6749 6절).

```
POST /realms/portal/token
  grant_type=refresh_token&refresh_token=...&client_id=portal-17kqqi85h2ks
```

## 왜 쿠키가 아닌가

access 토큰은 애초에 쿠키로 옮길 수 없다. 우리 도메인에 구운 쿠키는 customer-service 로 가는
요청에 실리지 않는다. 서비스가 여럿인 구성에서 쿠키는 토큰을 나를 수 없다.

refresh 토큰은 사정이 달라서 한동안 `HttpOnly` 쿠키로 내보냈다. 갈 곳이 auth 자신뿐이라
도메인이 갈리는 문제가 없었기 때문이다. 다시 걷은 이유는 셋이다.

- **로그인 방식마다 토큰이 있는 자리가 갈렸다.** 인가 코드 흐름이면 쿠키, 비밀번호나 소셜이면
  본문. 앱도 서버도 두 경우를 다 감당해야 했고, 재발급 엔드포인트는 쿠키와 본문을 둘 다 받았다
- **운영에서 안 통한다.** `portal.co.kr` 과 `auth.example.com` 처럼 사이트가 갈리면 그 쿠키는
  서드파티가 된다. `SameSite=None; Secure` 로 바꾸면 이번엔 브라우저의 서드파티 차단에 걸린다
- **표준 자리가 아니었다.** 쿠키로 받으려면 재발급이 우리가 지은 주소에 있어야 했다. 표준
  클라이언트는 발급자 문서가 가리키는 토큰 엔드포인트만 알고 그 주소는 찾아가지 못한다

## 그래서 치르는 값

토큰이 스크립트가 읽을 수 있는 자리에 놓인다. **XSS 가 나면 털린다.** 쿠키의 `HttpOnly` 가 막아
주던 것이 없어졌다. 남은 완화는 셋이고, 셋 다 "털렸을 때 얼마나 오래 쓰이나" 를 줄이는 것이지
털리는 것 자체를 막지는 못한다.

- access 토큰은 짧게 쓰고 **메모리**에 둔다. `localStorage` 는 탭을 닫아도 남는다
- refresh 토큰은 **회전**한다. 한 번 쓰면 죽고, 재사용이 보이면 계보가 끊긴다
  ([refresh 토큰 회전](refresh-토큰-회전.md))
- 토큰이 향할 시스템은 `aud` 로 좁힌다. 한 곳이 털려도 다른 시스템에 그대로 재생되지 않는다

제대로 막으려면 BFF 다. 토큰을 서버가 들고 브라우저는 **프론트와 같은 출처의** 세션 쿠키만 받는다.
그러면 도메인이 갈리는 문제도 `HttpOnly` 를 잃는 문제도 함께 풀린다. 이 저장소에는 아직 없다.

## 앱이 지켜야 하는 것

- **재발급 응답의 새 refresh 토큰을 반드시 저장한다.** 회전 때문에 방금 쓴 토큰은 죽었다.
  안 갈아끼우면 다음 재발급에서 계보가 끊기고 로그아웃된다
- **재발급을 한 번으로 묶는다.** 화면이 여러 요청을 동시에 띄우면 401 도 여럿이다. 각자
  재발급하면 진 쪽이 이미 쓴 토큰을 내게 되고, 그것이 계보를 끊는다
- **`credentials` 를 켜지 않는다.** 주고받을 쿠키가 없다. 서버도 `allowCredentials` 를 끄고 있어,
  켜면 그 요청은 CORS 에서 막힌다

## 어디에 있나

| 무엇 | 어디 |
|---|---|
| 토큰 엔드포인트 (교환·재발급) | `auth-web/.../web/authorize/TokenEndpointController.java` |
| 로그인 응답에 실리는 토큰 | `auth-web/.../web/support/IssuedTokens.java` |
| CORS (credentials 를 끄는 이유) | `auth-web/.../web/support/CorsConfiguration.java` |
| 발급자 문서 (`grant_types_supported`) | `auth-web/.../web/wellknown/OpenIdConfigurationApiController.java` |
| 토큰에 무엇이 실리나 | `auth-application/.../identity/token/RbacJwtTokenIssuer.java` |
| 앱 쪽 교환·재발급 | `frontends/portal/src/api/authorize.js` |
| 앱 쪽 401 재시도·재발급 묶기 | `frontends/portal/src/api/http.js`, `src/auth/AuthContext.jsx` |

## 아직 없는 것

- **BFF.** 이것이 있어야 `HttpOnly` 를 되찾는다. 지금 구조에서는 앱이 토큰을 들 수밖에 없다
- **DPoP.** 토큰을 그 브라우저에만 묶는 방법. 회전과 달리 탈취된 토큰을 처음부터 못 쓰게 한다
- **폐기.** 로그아웃해도 이미 나간 access 토큰은 만료까지 산다. 무상태 JWT 의 성질이다
- **수명 정리.** refresh(24시간)가 로그인 세션(8시간)보다 오래 산다. 순서가 거꾸로다
- **백오피스의 401 재시도.** 포털에만 있다. 백오피스는 화면의 버튼으로만 재발급한다
