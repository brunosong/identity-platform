# 토큰을 어디에 두나

토큰 둘이 같은 곳에 있지 않다. **가는 곳이 다르기 때문이다.**

| | 어디로 가나 | 어디에 두나 |
|---|---|---|
| access | customer-service, order-service, ... | 앱 메모리 + `Authorization` 헤더 |
| refresh | 재발급 엔드포인트 하나뿐 | **`HttpOnly` 쿠키** |

access 토큰은 쿠키로 옮길 수 없다. 우리 도메인에 구운 쿠키는 customer-service 로 가는 요청에
실리지 않는다. 그래서 본문으로 내리고 앱이 헤더에 싣는다. 스크립트가 읽을 수 있는 자리에
놓인다는 뜻이고, 그래서 짧게 쓰고 `localStorage` 에 넣지 않는다.

refresh 토큰은 사정이 다르다. 갈 곳이 auth 자신뿐이라 쿠키로 옮길 수 있다.

```
POST /realms/portal/token
  응답 본문:  { "access_token": "...", "token_type": "Bearer" }
                                       refresh_token 이 없다
  Set-Cookie: REFRESH_TOKEN=...; HttpOnly; SameSite=Lax;
              Path=/api/auth/realms/portal/token
```

**본문에 함께 싣지 않는 것이 요점이다.** 둘 다 주면 스크립트가 본문에서 읽어 보관할 수 있고,
그러면 `HttpOnly` 는 장식이 된다. 명세에서도 `refresh_token` 은 선택 항목이다(RFC 6749 5.1).

재발급할 때 앱은 아무것도 내지 않는다. 브라우저가 쿠키를 알아서 싣는다.

```js
// 앱 코드. 넘길 값이 없다
await request(auth, 'POST', '/api/auth/realms/portal/token/refresh', { withCookies: true });
```

## 경로를 좁히는 이유

`Path` 를 재발급 주소로 좁혀두면 **그 요청에만** 실린다. 좁히지 않으면 JWKS 조회, 권한 조회,
화면을 여는 모든 요청에 1KB 가 따라붙는다. `AUTH_SESSION` 을 `/realms/{realm}` 으로 좁힌 것과
같은 수법이다.

## 막는 것과 못 막는 것

막는 것은 **반출**이다. XSS 가 나도 공격자가 이 값을 자기 서버로 가져가지 못한다.

못 막는 것은 **피해자 브라우저 안에서 쓰는 것**이다. 쿠키는 브라우저가 알아서 붙이므로,
심어진 스크립트가 재발급을 부르면 새 access 토큰이 본문으로 나온다. 오래 사는 자격증명이
밖으로 나가지 않는다는 것만으로도 값을 하지만, 그것이 전부다.

## 아직 한 흐름뿐이다

쿠키로 옮긴 것은 **인가 코드 흐름 하나**다. 비밀번호·이메일 인증번호·소셜 로그인은 여전히
refresh 토큰을 본문으로 내린다. 그래서 재발급 엔드포인트가 쿠키와 본문을 둘 다 받고, 쿠키를
먼저 본다. **같은 앱인데 로그인 방법에 따라 refresh 토큰이 어디 있는지가 갈린다** - 마이페이지의
`refresh 토큰` 자리가 그것을 보여준다.

## 로컬에서 헷갈리는 자리

쿠키는 **포트를 구분하지 않는다**(RFC 6265). `localhost:8080` 이 구운 쿠키가 `localhost:5173`
과 같은 서랍에 들어가서, 개발자 도구에는 5173 밑에 보인다. 운영에서 도메인이 갈리면 안 섞인다.
`Path` 가 달라 실제로 5173 요청에 실리지는 않는다.

그리고 `credentials: 'include'` 가 없으면 **브라우저가 `Set-Cookie` 를 말없이 버린다.** 오류도
경고도 없고 Network 탭에는 헤더가 그대로 보인다. 서버 쪽에는 `allowCredentials(true)` 가 짝으로
필요하다.

## 어디에 있나

| 무엇 | 어디 |
|---|---|
| refresh 쿠키 속성 (경로, SameSite) | `auth-web/.../web/support/RefreshTokenCookie.java` |
| 쿠키를 심는 자리 | `auth-web/.../web/authorize/TokenEndpointController.java` |
| 쿠키를 읽는 자리 (재발급) | `auth-web/.../web/client/identity/AuthTokenApiController.java` |
| 본문에 실을 토큰 고르기 | `auth-web/.../web/support/IssuedTokens.java` |
| CORS credentials | `auth-web/.../web/support/CorsConfiguration.java` |
| 앱 쪽 쿠키 스위치 | `frontends/portal/src/api/http.js` |
| 앱 쪽 교환·재발급 | `frontends/portal/src/api/authorize.js`, `api/auth.js` |
| 화면에서 보여주는 자리 | `frontends/portal/src/pages/MyPage.jsx` |

## 아직 없는 것

- **나머지 로그인 경로.** 비밀번호·이메일 인증번호·소셜은 아직 refresh 토큰을 본문으로 내린다.
  옮기면 재발급 엔드포인트의 본문 갈래를 지울 수 있다
- **회전.** refresh 토큰에 `jti` 같은 고유값이 없어서, 같은 초에 재발급하면 글자까지 같은 토큰이
  나온다. 한 번 쓰면 폐기하고 재사용을 감지하려면 저장소가 필요하다
- **폐기.** 로그아웃해도 refresh 토큰이 죽지 않는다. 쿠키는 지울 수 있지만 이미 복사해 간 값은
  못 막는다
- **수명 정리.** refresh(24시간)가 세션(8시간)보다 오래 산다. 순서가 거꾸로다
- **401 자동 복구.** 앱이 만료를 만나면 화면에 오류만 뜬다. 재발급을 자동으로 부르지 않는다
