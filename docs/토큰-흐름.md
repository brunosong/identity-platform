# 토큰 흐름

로그인 요청 한 줄이 어떻게 토큰이 되고, 그 토큰이 서비스에서 어떻게 401 과 403 으로 갈리는지.
전 구간을 한 장에 적는다.

## 먼저, 네 개를 구분한다

이 네 가지가 헷갈리면 나머지가 다 안 읽힌다. 서로 다른 질문에 답한다.

| | 예 | 답하는 질문 | 토큰 어디 |
|---|---|---|---|
| **realm** | `PORTAL` | 어느 서랍에서 계정을 찾나 | `iss` (서명키가 증명한다) |
| **앱** | `customer-portal` | 누가 토큰을 받아갔나 | `azp` |
| **시스템** | `shop` | 이 토큰을 누가 받아주나 | `aud` |
| **서비스** | `order-service` | 그 안에서 무엇을 할 수 있나 | `resource_access` 의 칸 |

**시스템은 마이크로서비스의 집합**이다. `shop` 안에 `customer-service` 와 `order-service` 가 있다.

> 시스템 이름을 realm 과 다르게 지었다. 로그인 경로는 `/realms/portal` 인데 시스템은 `shop` 이다.
> 같은 글자를 쓰면 둘이 다른 개념이라는 사실이 이름에서 지워진다.

## 1. 로그인 요청

```
POST /api/auth/realms/portal/login
{"loginId":"hong@example.com", "password":"pw12345678", "clientId":"customer-portal"}
```

요청이 정하는 것은 둘뿐이다.

- **경로의 `portal`** → `Realm.PORTAL`. 어느 서랍에서 계정을 찾을지
- **본문의 `clientId`** → `customer-portal`. 어느 앱이 요청했는지

**시스템은 요청에 없다.** 요청이 주장할 수 있는 값으로 두면 아무나 `aud` 를 골라잡을 수 있다.

## 2. auth 가 clientId 로 시스템을 찾는다

```yaml
# auth-service/auth-bootstrap/src/main/resources/application.yml
token:
  clients:
    customer-portal:
      realm: PORTAL
      system: shop        # ← 이것이 aud 가 된다
    employee-admin:
      realm: ADMIN
      system: backoffice
```

```java
// RbacJwtTokenIssuer.issue()
String systemId = clients.systemOf(realm, clientId);   // "shop"
```

realm 도 함께 대조한다. 어드민 앱이 포털 realm 으로 로그인해 어드민 시스템 토큰을 얻는 길을 막는다.
모르는 앱이거나 realm 이 어긋나면 **401** 이다. 400 이 아닌 것은, 어떤 `clientId` 가 존재하는지
응답으로 훑을 수 없게 하려는 것이다.

### 왜 clientId 를 그대로 aud 로 쓰지 않나

`clientId` 를 `shop-system` 같은 이름으로 짓고 그대로 `aud` 에 실으면 이 매핑이 필요 없다. 앱이
하나뿐이면 실제로 그 편이 단순하다.

**앱이 둘이 되는 순간 갈린다.** 웹과 모바일이 같은 백엔드를 쓰는 것은 흔한 일이다.

```
앱                        시스템        서비스
customer-portal (웹)  ─┐
customer-mobile (앱)  ─┼──>  shop  ──>  customer-service
ops-console           ─┘                order-service
```

`aud` 가 `clientId` 라면 세 앱이 각각 다른 `aud` 를 만들고, **백엔드가 프론트엔드 목록을 알아야 한다.**

```yaml
# customer-service 가 이렇게 된다
audiences: customer-portal,customer-mobile,ops-console
```

앱을 하나 붙일 때마다 모든 백엔드 서비스의 설정을 고쳐야 한다. 이것은 `aud` 에 서비스를 나열했을
때 겪은 것과 **같은 문제가 축만 바뀐 것**이다. 그때는 서비스를 붙일 때 auth 를 재배포해야 했고,
이번에는 앱을 붙일 때 모든 백엔드를 재배포해야 한다.

방향도 거꾸로다. 백엔드는 **어느 앱에서 왔는지 몰라도 되는** 것이 맞다. 그것을 알아야 할 일이 생기면
그때 보라고 `azp` 를 따로 싣는다.

> Keycloak 도 같다. `client_id` 는 앱이고 `aud` 는 따로 정해진다. 둘을 합치면 앱마다 다른 TTL 을
> 주거나 한 앱의 자격증명만 회전시키는 것 같은 일도 못 하게 된다.

## 3. 그 시스템의 권한만 읽는다

`resource_access` 는 설정이 아니라 **DB 를 조인해 나온 결과**다.

```
authz_subject_role     이 사람의 역할          →  CUSTOMER
      │
authz_role_permission  그 역할의 권한          →  PROFILE_READ, ORDER_READ, ORDER_WRITE
      │
authz_permission       그 권한이 어느 서비스 것 →  customer-service / order-service
      │
authz_service          그 서비스가 어느 시스템  →  shop 인 것만 남긴다
```

마지막 조인이 `aud` 와 이어지는 자리다. `shop` 에 속한 서비스의 권한만 실린다. 전부 실으면 토큰이
realm 전체 크기로 자라고, 다른 시스템의 권한까지 새어 나간다.

```sql
-- AuthzSubjectRoleJpaRepository.findServicePermissionCodes
SELECT DISTINCT p.serviceId, p.permissionCode
  FROM AuthzSubjectRoleEntity sr
  JOIN AuthzRoleEntity r ON sr.roleId = r.roleId
  JOIN r.permissions p
  JOIN AuthzServiceEntity s ON s.serviceId = p.serviceId
 WHERE s.systemId = :systemId      -- ← 여기
```

**서비스를 하나 붙이는 일은 이 표에 한 줄이다.** auth 설정도, `aud` 도, 이미 발급된 토큰도 그대로다.

```sql
INSERT INTO authz_service (service_id, realm, system_id, service_name, ...)
VALUES ('order-service', 'PORTAL', 'shop', 'Order service', ...);
```

## 4. 나온 토큰

```json
{
  "iss": "http://localhost:8080/realms/portal",
  "aud": ["shop"],
  "azp": "customer-portal",
  "sub": "a4120a37-54c1-4cce-9805-a6b05a435b67",
  "type": "access",
  "realm_access":    { "roles": ["CUSTOMER"] },
  "resource_access": {
    "customer-service": { "roles": ["PROFILE_READ"] },
    "order-service":    { "roles": ["ORDER_READ", "ORDER_WRITE"] }
  },
  "rbacRev": 1
}
```

`realm` 클레임은 없다. realm 마다 서명키가 다르니 **어느 키로 검증됐는지가 곧 realm** 이고, 그것을
표준 자리에서 밝히는 값이 `iss` 다.

## 5. 서비스가 이 토큰을 받는다

여기가 요점이다. **두 단계로 갈리고, 실패 코드가 다르다.**

| | 보는 값 | 어디서 | 실패하면 |
|---|---|---|---|
| **문** | 서명, `exp`, `iss`, `aud` | Spring Security 필터 (설정) | **401** |
| **방** | `resource_access["order-service"]` | matcher (`SecurityConfiguration`) | **403** |

### 문: 이 토큰을 받아들일까

```yaml
# order-service
spring.security.oauth2.resourceserver.jwt:
  issuer-uri: http://localhost:8080/realms/portal   # realm 경계
  audiences: shop                                    # 시스템 경계
```

`customer-service` 도 **똑같이 `shop`** 을 요구한다. 그래서 한 번 로그인한 토큰 하나가 둘 다 통과한다.
이것이 통합 로그인이다.

어드민 토큰은 여기서 죽는다. `aud` 가 `backoffice` 이기도 하고, 그 전에 어드민 realm 의 키로 서명돼
있어 이 서비스가 가진 JWKS 로는 서명 검증조차 안 된다.

### 방: 들어와서 무엇을 할까

문을 통과했다고 아무것도 열리지 않는다.

```java
// order-service ClientRoleAuthorities
@Value("${app.service-id}") String serviceId       // "order-service"
resource_access[serviceId].roles → Spring Security authority
```

```java
// order-service SecurityConfiguration
.requestMatchers(HttpMethod.POST, "/api/orders").hasAuthority("ORDER_WRITE")
.requestMatchers("/api/orders/**").hasAuthority("ORDER_READ")
.anyRequest().authenticated()
```

`aud` 가 맞아도 `order-service` 칸이 없으면 **403** 이다. 401 이 아닌 것이 요점이다. 토큰은 멀쩡한데
권한이 없다는 뜻이다.

`customer-service` 칸에 `ORDER_WRITE` 를 넣어 둬도 order-service 는 열리지 않는다. 각 서비스가
`app.service-id` 로 **자기 칸만** 읽기 때문이다. `aud` 가 같아진 지금은 이것만이 두 서비스를 가른다.

> 테스트로 고정해 뒀다. `MyOrderApiSecurityTest.rolesOfAnotherServiceOpenNothingHere`

## 6. 세 가지 경계가 어디 있나

| 막는 것 | 어디서 | 잊으면 |
|---|---|---|
| 다른 realm | 서명키 (JWKS 가 realm 별) | 애초에 검증이 안 된다 |
| 다른 시스템 | 설정 (`audiences`) | 다른 시스템 토큰이 통한다 |
| 같은 시스템의 다른 서비스 | `resource_access` 칸 | 남의 서비스 권한이 문을 연다 |
| **이 데이터가 이 사람 것인가** | **컨트롤러** | **남의 데이터가 열린다** |

마지막 줄만 코드에 있다. 토큰은 "이 사람이 누구인가" 까지만 답하고 "이 데이터가 이 사람 것인가" 는
답하지 못한다. 게이트웨이가 생겨도 이 확인은 대신해 줄 수 없다.

## 통합 로그인과 시스템이 여럿일 때

realm 하나에 시스템이 여럿일 수 있다. 하지만 **토큰 하나는 시스템 하나를 향한다.**
`aud: shop,loyalty` 같은 것을 쓰지 않는다.

통합 로그인은 **세션**이 맡는 일이다.

```
시스템 A 로 로그인  ->  auth 세션 생김   ->  A 용 토큰 (aud=A)
시스템 B 로 이동    ->  세션이 이미 있음  ->  화면 없이 B 용 토큰 (aud=B)
```

사용자 눈에는 로그인 한 번이고 토큰은 둘이다. OIDC 도 Keycloak 도 이렇게 돈다.

`aud` 에 나열하면 시스템을 늘릴 때 auth 를 재배포해야 하고, 이미 발급된 access 토큰은 재발급
전까지 새 시스템에 닿지 못한다. 거기에 시스템 경계까지 잃는다. 시스템은 보통 팀도 배포 주기도 다른데, `loyalty` 가 뚫리면 거기
들어온 토큰이 `shop` 에 그대로 통하게 된다.

> 두 번째 시스템이 실제로 생기면 refresh 로 다른 시스템용 access 를 받는 경로를 연다. 재료는 이미
> 있다(refresh 토큰의 `cid`, 세션의 `sid`). 지금은 시스템이 하나뿐이라 만들지 않았다.

## 무엇을 늘릴 때 어디를 고치나

| 늘리는 것 | 고칠 곳 | 기존 토큰 |
|---|---|---|
| 서비스 (`order-service`) | **DB 한 줄** (`authz_service`) | **그대로 통한다** |
| 앱 (`customer-mobile`) | auth 설정 `token.clients` 한 항목 (재배포) | 무관 |
| 시스템 (`loyalty`) | auth 설정 `token.realms.*.systems` (재배포) | 그 시스템 토큰을 새로 받는다 |
| realm | 키페어 + 설정 (재배포) | 무관 (다른 서랍이다) |

첫 줄이 이 설계의 목적이다. 마이크로서비스를 늘리는 일은 가장 자주 일어나고, 그때 auth 를
재배포하지 않아야 한다.

> **재발급에 관해 정확히.** 설정으로 `aud` 를 정하던 시절에도 "전원 재로그인" 까지는 아니었다.
> 재발급이 `issue()` 를 그대로 다시 타므로 refresh 만으로 새 `aud` 가 실린다. 문제는 auth
> 재배포가 필요했다는 것과, 이미 발급된 access 토큰이 만료될 때까지(기본 2시간) 새 서비스에
> 닿지 못하는 창이 생긴다는 것이었다.
