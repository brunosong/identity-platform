# 토큰 흐름

로그인 요청 한 줄이 어떻게 토큰이 되고, 그 토큰이 서비스에서 어떻게 확인되는지.

## 토큰은 신원만 답한다

```json
{
  "iss":  "http://localhost:8080/realms/portal",
  "aud":  ["shop"],
  "sub":  "2f231b51-7703-42b8-aa13-fa906fd57dc6",
  "type": "access",
  "iat":  1789476440,
  "exp":  1789483640
}
```

이게 전부다. **역할도 권한도 싣지 않는다.**

한때 `realm_access`, `resource_access`, 그리고 그것이 낡았는지 가리는 `rbacRev` 까지 실려 있었다.
토큰 하나가 신원과 인가를 겸하면서 같은 판단이 세 군데(토큰 클레임, auth 의 authz 표, 소비 서비스의
matcher)에 나뉘어 읽기 어려웠다. 인가를 어디서 판정할지는 아직 정하지 않았고, 정할 때까지 토큰은
"이 요청이 누구인가" 만 답한다.

## 세 값이 무엇을 답하나

| | 예 | 답하는 질문 | 무엇이 보장하나 |
|---|---|---|---|
| `iss` | `.../realms/portal` | 어느 realm 이 발급했나 | **서명키.** realm 마다 키가 다르다 |
| `aud` | `shop` | 어느 **시스템**이 받아주나 | 설정 대조 |
| `sub` | `2f231b51-...` | 누구인가 | 서명 |

**시스템은 마이크로서비스의 집합이다.** `shop` 안에 `customer-service` 와 `order-service` 가 있다.

> 시스템 이름을 realm 과 다르게 지었다. 로그인 경로는 `/realms/portal` 인데 시스템은 `shop` 이다.
> 같은 글자를 쓰면 둘이 다른 개념이라는 사실이 이름에서 지워진다.

`realm` 클레임은 없다. realm 마다 서명키가 다르니 **어느 키로 검증됐는지가 곧 realm** 이고, 그것을
표준 자리에서 밝히는 값이 `iss` 다.

## iss 와 aud 는 어디서 오나

둘 다 **설정에서 와서 코드가 조립한다.** 요청은 어느 쪽도 고르지 못한다.

| | 설정 | 만드는 곳 | 결과 |
|---|---|---|---|
| `iss` | `token.issuer` | `RealmIssuers.of(realm)` | `{issuer}/realms/portal` |
| `aud` | `token.realms.PORTAL.system` | `RealmSystems.of(realm)` | `shop` |

```yaml
token:
  issuer: http://localhost:8080      # iss 의 앞부분
  realms:
    PORTAL:
      system: shop                   # 이것이 aud 가 된다
      kid / privateKey / publicKey   # 이 키가 iss 를 증명한다
```

**realm 은 소문자로 붙인다.** JWKS 경로(`/realms/portal/.well-known/jwks.json`)와 같은 표기여야
두 값이 어긋나지 않는다. 그래서 `iss + "/.well-known/jwks.json"` 이 그 realm 의 공개키 주소가
된다. 소비 서비스가 발급자 하나만 알면 되는 이유다.

**`token.issuer` 가 없으면 부팅에서 막는다.** 발급자 없이 뜨면 그 뒤로 나가는 모든 토큰이
발급자 없는 토큰이 되고, 그 사실은 소비 서비스가 검증에 실패할 때에야 드러난다.

### 옮길 때 무엇을 고치나

`iss` 는 **주소이면서 이름**이다. 그래서 배포를 옮기면 두 쪽이 함께 움직여야 한다.

```
auth 의  token.issuer                     를 바꾸면
소비 서비스의  issuer-uri                  도 같이 바꿔야 한다
```

한쪽만 고치면 서명도 realm 도 맞는 토큰이 발급자 이름 때문에 거절된다. 그것이 의도한 동작이다.
staging 의 포털 토큰과 prod 의 포털 토큰은 클레임이 완전히 같아서, 둘을 가르는 값은 `iss` 뿐이다.

`aud` 쪽은 반대다. **서비스를 늘려도 값이 바뀌지 않는다.** 서비스는 시스템 안의 구성요소라
`authz_service` 에 한 줄 넣으면 끝이고, 이미 발급된 토큰도 그대로 그 서비스에 닿는다.

## 1. 토큰 요청

사람은 auth 의 로그인 화면에서 로그인하고, 앱은 받은 code 를 토큰 엔드포인트에서 바꾼다
([인가 코드 흐름](인가-코드-흐름.md)). 토큰을 바로 내주는 로그인 API 는 없다.

```
POST /realms/portal/token
grant_type=authorization_code&code=...&client_id=portal-17kqqi85h2ks&redirect_uri=...&code_verifier=...
```

요청이 정하는 것은 **경로의 realm 하나**다. `portal` → `Realm.PORTAL`, 즉 어느 서랍에서 계정을
찾았고 어느 키로 서명할지다.

## 2. realm 이 시스템을 정한다

```yaml
token:
  realms:
    PORTAL:
      system: shop        # ← 이것이 aud 가 된다
    ADMIN:
      system: backoffice
```

```java
// RbacJwtTokenIssuer.issue()
String systemId = systems.of(realm);   // "shop"
```

**시스템은 요청에 없다.** 요청이 주장할 수 있는 값으로 두면 아무나 `aud` 를 골라잡을 수 있다.

### 왜 앱(clientId)이 고르지 않나

한때 로그인 요청이 `clientId` 를 함께 보내고, 그 앱이 속한 시스템을 `aud` 로 썼다.

```
POST /realms/portal/login
{"loginId":"...", "password":"...", "clientId":"portal"}   ← 이랬다
```

그런데 realm 과 시스템이 1:1 이라 **앱은 새 정보를 더하지 않았다.** 경로가 `portal` 이면 시스템은
`shop` 으로 정해져 있다. 프론트엔드도 realm 과 clientId 를 둘 다 상수로 박아 늘 같은 짝으로 보냈다.

대신 입력이 둘이 되면서 **어긋날 수 있는 자리**가 생겼다. "포털 앱으로 어드민 realm 토큰 요청" 같은
실패 모드는 `clientId` 가 없으면 성립조차 하지 않는다. 자기가 만든 문제를 자기가 막고 있었던 셈이다.
realm 격리를 실제로 지키는 것은 서명키다.

**한 realm 에 시스템이 둘 이상 필요해지면** 경로만으로 정할 수 없으므로 고를 값이 다시 필요하다.
그때 들인다. 지금 미리 두지 않는 이유는, 값이 있어도 고를 것이 하나뿐이라 아무 판단도 하지 않기
때문이다.

### 왜 aud 에 서비스를 적지 않나

처음에는 `aud: customer-service,order-service` 로 나열했다. 그러면 서비스를 하나 붙일 때마다
**auth 를 재배포**해야 했고, 이미 발급된 access 토큰은 만료돼 재발급될 때까지 새 서비스에 닿지
못했다. 내부 분해가 토큰에 새어나가서 생긴 일이다.

지금은 `aud` 가 `shop` 으로 고정이다. 서비스를 붙이는 일은 DB 에 한 줄이다.

```sql
INSERT INTO authz_service (service_id, realm, system_id, service_name, ...)
VALUES ('order-service', 'PORTAL', 'shop', 'Order service', ...);
```

### 시스템을 여럿 적지 않는다

realm 하나에 시스템이 여럿일 수 있다. 하지만 **토큰 하나는 시스템 하나를 향한다.**
`aud: shop,loyalty` 같은 것을 쓰지 않는다.

통합 로그인은 **세션**이 맡는 일이다.

```
시스템 A 로 로그인  ->  auth 세션 생김   ->  A 용 토큰 (aud=A)
시스템 B 로 이동    ->  세션이 이미 있음  ->  화면 없이 B 용 토큰 (aud=B)
```

사용자 눈에는 로그인 한 번이고 토큰은 둘이다. OIDC 도 Keycloak 도 이렇게 돈다.

나열하면 시스템 경계를 잃는다. 시스템은 보통 팀도 배포 주기도 다른데, `loyalty` 가 뚫리면 거기 들어온
토큰이 `shop` 에 그대로 통하게 된다.

## 3. 서비스가 이 토큰을 받는다

```yaml
# customer-service, order-service 가 똑같이
spring.security.oauth2.resourceserver.jwt:
  issuer-uri: http://localhost:8080/realms/portal   # realm 경계
  audiences: shop                                    # 시스템 경계
```

두 서비스가 **같은 값**을 요구한다. 그래서 한 번 로그인한 토큰 하나가 둘 다 통과한다.

어드민 토큰은 여기서 죽는다. `aud` 가 `backoffice` 이기도 하고, 그 전에 어드민 realm 의 키로 서명돼
있어 이 서비스가 가진 JWKS 로는 서명 검증조차 안 된다.

### 지금 역할 검사는 없다

토큰에 역할이 없으니 `hasAuthority(...)` 도 없다. **인증만 통과하면 API 가 열린다.**

```java
.authorizeHttpRequests(requests -> requests
        .anyRequest().authenticated())
```

권한 데이터 자체는 auth 에 그대로 있다(`authz_role`, `authz_permission`, `authz_service`).
없어진 것은 그것을 토큰으로 나르던 길뿐이다. 소비 서비스가 어떻게 판정할지는 다음에 정한다.

## 4. 인가가 빠져도 서는 것 둘

| | 막는 것 | 어디서 |
|---|---|---|
| **시스템 경계** | 다른 시스템 앞으로 발급된 토큰 | 설정 (`audiences`) → 401 |
| **소유권** | 이 데이터가 이 사람 것인가 | 컨트롤러 → 404 |

둘 다 역할과 무관하다.

**소유권이 역할이 아니라는 것**이 이 저장소에서 보여주려는 것 중 하나다. `/api/orders/{orderId}` 는
남의 주문번호를 적어 넣을 수 있는 자리인데, 조회 조건에 `sub` 를 함께 걸어서 막는다.

```java
orders.findOwned(token.getSubject(), orderId)   // 주문번호만으로 찾는 길이 없다
```

남의 주문은 **403 이 아니라 404** 다. 403 이면 "그 주문은 존재한다" 가 새어나가고, 번호를 훑어
남의 주문을 셀 수 있다.

## auth 자신은 어떻게 하나

auth 의 관리 API(`/api/admin/**`)는 열리면 안 된다. 스프링 시큐리티 체인이 ADMIN 키로 토큰을 검증하고,
권한은 **DB 를 조회해** 채운 뒤 `AUTHZ_MANAGE` 가 있는지 본다.

```java
// SecurityConfiguration.adminApi 의 변환기
subjectPermissions.of(Realm.ADMIN, jwt.getSubject())   // authz 표를 직접 읽어 authorities 로
```

auth 는 authz 표를 쥐고 있으므로 이 선택지가 있다. 요청마다 DB 를 한 번 더 타는 대가로 **권한 회수가
즉시 반영**된다. 토큰에 실어 두었을 때는 그 토큰이 만료될 때까지 살아 있었다.

**소비 서비스는 같은 선택지를 갖지 못한다.** auth 의 DB 가 없기 때문이다. 그 자리를 어떻게 채울지가
남은 문제다.

## 무엇을 늘릴 때 어디를 고치나

| 늘리는 것 | 고칠 곳 | 기존 토큰 |
|---|---|---|
| 서비스 (`order-service`) | **DB 한 줄** (`authz_service`) | **그대로 통한다** |
| 시스템 (`loyalty`) | auth 설정 `token.realms.*.system` (재배포) | 그 시스템 토큰을 새로 받는다 |
| realm | 키페어 + 설정 (재배포) | 무관 (다른 서랍이다) |

첫 줄이 이 설계의 목적이다. 마이크로서비스를 늘리는 일은 가장 자주 일어나고, 그때 auth 를
재배포하지 않아야 한다.

## 아직 정하지 않은 것

- **인가를 어디서 판정하나.** 게이트웨이, 소비 서비스의 auth 조회, 토큰 재적재 중 무엇으로 갈지
- **시스템의 집.** `authz_service.system_id` 는 컬럼일 뿐이고 아무도 검사하지 않는다. 오타를 내면
  그 서비스가 조용히 사라진다
