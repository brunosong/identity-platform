# MSA 인가 방식

서비스가 나뉜 뒤 "이 사람이 이 일을 해도 되나" 를 어디서 판정할지 정리한 문서다. 지금 무엇을
하고 있고, 서비스가 늘면 어디서 막히고, 다음에 어느 쪽으로 갈지를 담는다.

**상태: 방향 제안까지. 아직 정하지 않았다.** 지금 코드는 아래 "지금 하는 것" 까지다.

## 질문을 둘로 나눈다

"권한 관리를 어디서 하나" 는 두 질문이 섞인 말이다.

- **데이터를 누가 갖나.** 누구에게 어떤 역할이 있고, 역할에 어떤 권한이 있나
- **누가 판정하나.** 요청이 왔을 때 통과시킬지 정하는 자리

둘은 따로 정할 수 있다. 전자정부 프레임워크는 모놀리스라 둘이 한 프로세스 안에 있었다.

## 흔히 쓰는 다섯 가지

| | 데이터 | 판정 | 예 |
|---|---|---|---|
| 1. 게이트웨이 | 게이트웨이 설정 | 게이트웨이 | Spring Cloud Gateway, Kong |
| 2. 각 서비스 | 각 서비스 DB | 각 서비스 | 서비스마다 자기 권한 표 |
| 3. 토큰에 싣기 | 중앙(auth) | 각 서비스 (토큰만 보고) | Keycloak `realm_access`, `resource_access` |
| 4. 중앙 판정 서비스 | 중앙 | 중앙 (매번 물어봄) | OpenFGA, SpiceDB, Keycloak Authorization Services |
| 5. 정책을 코드로 배포 | Git | 서비스 옆 엔진 | OPA, AWS Cedar |

실제로는 섞는다. 층마다 맡는 일이 다르다.

```
게이트웨이     로그인했나, 이 경로에 들어올 수 있나        거칠게
서비스 진입    토큰의 역할/권한으로 이 API 를 부를 수 있나   3번
서비스 안      이 주문이 이 사람 것인가                    2번. 데이터를 봐야 한다
```

마지막 층은 어느 방식을 써도 서비스에 남는다. 주문 데이터는 order-service 만 갖고 있다.

## 지금 하는 것

3번이다. auth 가 access 토큰의 `realm_access.roles` 에 역할을 싣고, order-service 가
`hasRole("CUSTOMER")` 로 판정한다. 소유권은 `findOwned(customerId, orderId)` 가 따로 본다.
역할은 발급할 때마다 다시 읽어서 refresh 하면 바뀐 역할이 실린다.

이 저장소는 4번에서 왔다. auth 의 `authz_url_access` 와 `CheckAccessUseCase` 가 요청마다 묻는
방식이었다. 지금은 auth 콘솔 자신(MASTER)을 지키는 데만 쓴다.

## url-access 는 서비스 코드에 있다

전자정부는 URL 과 권한의 매핑을 DB(`COMTNSECURED_RESOURCES`)에 두었다. order-service 는 그것을
`SecurityConfiguration` 의 `requestMatchers(...)` 몇 줄로 둔다. 하는 일은 같고 적는 자리가 다르다.

| | auth DB 에 둔다 | 서비스 코드에 둔다 |
|---|---|---|
| API 하나 추가 | 서비스 배포와 auth 행 추가가 함께 맞아야 한다 | 서비스 배포 하나 |
| auth 가 아는 것 | 모든 서비스의 URL 구조 | 권한 이름뿐 |
| 운영 중 변경 | 화면에서 바로 | 재배포 |

운영 중에 자주 바꾸는 것은 "이 URL 에 무슨 권한" 이 아니라 "누가 이 기능을 쓰나" 다. 앞의 것은
API 를 고칠 때만 바뀌므로 코드와 함께 둔다. 뒤의 것은 역할-권한 연결이라 auth 콘솔에서 바꾼다.

## 역할과 권한

역할은 조직의 언어이고 권한은 기능의 언어다.

| | 예 | 바뀌는 때 | 쓰는 곳 |
|---|---|---|---|
| 역할 | CUSTOMER, VIP, 상담원 | 조직이 바뀔 때 | 사람에게 권한 묶음을 줄 때, 가입 시 기본 부여, 화면 분기, 감사 |
| 권한 | ORDER_READ, ORDER_WRITE | API 를 고칠 때 | 서비스의 API 판정 |

서비스가 `hasRole("CUSTOMER")` 를 쓰면 서비스 코드에 조직 구조가 들어온다. "상담원도 주문을
넣게" 하려면 서비스를 고쳐 배포해야 한다. `hasAuthority("ORDER_WRITE")` 면 auth 콘솔에서 상담원
역할에 그 권한을 붙이면 끝이다. 지금의 `hasRole` 은 권한을 나르는 길이 없어서 쓰는 임시 상태다.

전자정부 공통컴포넌트는 이름이 반대다. 거기의 "권한"(`ROLE_ADMIN`)이 우리의 역할이고, "롤"이
우리의 권한이다. 3계층 구조는 같다.

## Keycloak 은 둘 다 싣는다

기본 설정(Full scope allowed)이면 realm role 은 `realm_access` 에, 모든 클라이언트의 client role 은
`resource_access` 에 들어간다. composite role 은 끝까지 펼친다. 우리의 `authz_role_permission` 이
composite 와 같은 자리다.

## 서비스가 늘면 토큰이 커진다

같은 `aud`(`shop`)를 쓰는 서비스가 50개면 그 사람이 가진 50개 서비스의 권한이 전부 한 토큰에
실린다. 크기를 정하는 것은 시스템의 권한 수가 아니라 **그 사람이 가진 권한 수**다.

| 사람 | 권한 수 | 크기 |
|---|---|---|
| 일반 고객 | 50~100 | 1.5~3 KB |
| 운영자 | 수백 | 8 KB 넘음 |

Tomcat 과 nginx 의 헤더 한계가 기본 8 KB 이고 쿠키는 4 KB 다. 넘으면 권한 많은 사람만 400 을 받는다.
realm 이나 `aud` 로 거르는 것은 시스템이 다를 때만 줄여 준다. 같은 시스템 안에서는 소용없다.

## 줄이는 세 갈래

| | 토큰 | 반영 | 요청당 추가 호출 | 서비스가 할 일 |
|---|---|---|---|---|
| 권한을 다 싣기 (`resource_access`) | 서비스 수에 비례 | access 만료 (1분) | 없음 | 변환기 |
| **갈래 1. 역할만 싣고 역할-권한 표는 서비스가 캐시** | 작다 | 캐시 갱신 주기 | 없음 | 캐시와 갱신 |
| 갈래 2. 서비스별 토큰 (Token Exchange, Phantom Token) | 작다 | 교환 시점 | 교환 1회 | 거의 없음 |
| 갈래 3. 물어보기 (4번) | 작다 | 즉시 | 매번 1회 | 호출 |

## 제안: 갈래 1

```
토큰           realm_access.roles: ["CUSTOMER"]
order-service  CUSTOMER -> [ORDER_READ, ORDER_WRITE]   자기 service_id 몫만 캐시
                    ^
               auth 가 원본을 갖는다. 서비스가 기동할 때, 그리고 몇 분마다 받아 간다
```

- 토큰은 지금 모양 그대로다. 역할은 사람당 몇 개라 서비스가 늘어도 커지지 않는다
- 관리는 auth 콘솔 한곳이다. 원본은 `authz_role_permission` 이다
- 서비스 코드는 `hasAuthority` 만 쓴다. 역할 이름이 서비스에 박히지 않는다
- 게이트웨이도 메시지 브로커도 처음에는 필요 없다

순서는 이렇게 본다.

1. auth 에 서비스용 조회 API. 그 서비스 몫의 역할-권한 표를 준다
2. order-service 가 표를 받아 캐시하고, 토큰의 역할을 그 표로 권한으로 바꾼다
3. 규칙을 `hasRole` 에서 `hasAuthority` 로 바꾼다

## 정하지 않은 것

- **갈래 1 로 갈지.** 서비스가 둘인 지금은 `resource_access` 에 다 실어도 당장 문제가 없다
- **1번 API 의 인증.** 서비스가 부르는 API 라 서비스 자신의 인증(client credentials)이 필요하다.
  처음부터 만들지, 로컬에서는 열어 두고 시작할지
- **갱신 방식.** 주기적으로 다시 받기로 시작하고, 즉시 반영이 필요해지면 이벤트로 바꾼다
- **`authz_url_access` 의 앞날.** auth 콘솔 자신의 URL 이라 위 표의 문제가 없다. 남겨도 된다
- **데이터 단위 공유.** "이 주문을 가족과 공유" 같은 요구가 생기면 역할로는 안 된다. 그때 4번의
  관계 기반(OpenFGA)을 본다
