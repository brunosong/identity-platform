# 주문

포털 상세 화면에서 수량을 골라 주문하고, `/orders` 에서 내 주문을 본다. 주문은 order-service(:8082)
가 받는다. 이 기능의 요점은 **브라우저가 보낸 값 중 무엇을 믿고 무엇을 믿지 않느냐**다.

## 왜 이렇게 하나

주문 API 는 전부터 있었지만 가격을 브라우저가 보냈고, 상품과 재고는 프론트 배열에만 있었다.

| | 전 | 후 |
|---|---|---|
| 주문 본문 | `{productName, quantity, unitPrice}` | `{productId, quantity}` |
| 가격을 정하는 쪽 | 브라우저 | order-service 의 `products` 표 |
| 재고 | 프론트 배열의 숫자. 줄지 않는다 | 서버가 주문마다 줄인다 |
| 품절 상품 주문 | 막을 방법이 없다 | 409 |
| 화면에 보이는 가격과 재고 | 프론트 배열 | `GET /api/products` |

전에는 개발자 도구에서 `unitPrice: 0` 으로 고쳐 보내면 25만 원짜리 키보드가 0원에 주문됐다.
주문자를 본문으로 받지 않는 것과 같은 이유다. 받으면 보내는 쪽이 정할 수 있다.

## 한눈에 보는 흐름

```
 포털 (:5173)                          order-service (:8082)
 ─────────────                         ─────────────────────
 목록, 상세 ── GET /api/products ───>  products 표 읽기         (토큰 없음)
            <── 이름, 가격, 재고 ────

 [주문하기] ── POST /api/orders ────>  1. 토큰 검증 (iss, aud, 서명)
   Bearer access                          CUSTOMER 역할        없으면 403
                                       2. 상품 찾기           없으면 404
   {productId, quantity}               3. 주문 만들기          수량 < 1 이면 400
                                          금액 = 표의 가격 x 수량
                                       4. 재고 줄이기          모자라면 409
                                          (조건 건 UPDATE 한 번)
                                       5. 주문 저장
            <── 주문 (금액 포함) ─────    3~5 가 한 트랜잭션
   재고 다시 읽기

 /orders ───── GET /api/orders ─────>  토큰의 sub 로만 찾는다
```

## 왜 그렇게 도나

**재고는 읽고 비교해서 줄이지 않는다.** `UPDATE ... SET stock = stock - :q WHERE stock >= :q` 한
문장으로 줄이고, 바뀐 행이 0 이면 모자란 것이다. 읽고, 비교하고, 저장하는 세 걸음으로 나누면
마지막 하나를 두 사람이 동시에 살 때 둘 다 통과한다. 한 문장이면 데이터베이스가 하나만 통과시킨다.

**주문을 먼저 만들고 재고를 나중에 줄인다.** 수량 검증이 `Order.place` 안에 있기 때문이다. 재고를
먼저 줄이면 음수 수량이 검증보다 먼저 닿아 재고가 늘어난다.

**상품 표에 이름이 있는데 주문에도 이름을 남긴다.** 주문의 `product_name` 은 주문 당시의 이름이다.
상품 이름이 바뀌어도 지난 주문은 그때 이름으로 보여야 한다. 상품을 다시 찾는 열쇠는
`product_id` 이고, 그 칸이 생기기 전 주문에는 값이 없어 NULL 을 허용한다.

**상품 값이 두 곳에서 온다.** 이름, 가격, 재고는 서버가, 설명, 사양, 색은 프론트 배열이 준다.
주문 판단에 쓰이는 값만 서버로 옮겼다. 둘을 합치는 일은 `data/products.js` 한 곳에서 한다.

**상품 목록만 로그인 없이 열린다.** 누구에게나 같은 값이다. 나머지는 전처럼 인증이 필요하다.

**상품 하나만 주는 API 가 없다.** 상세 화면은 목록을 받아 그 안에서 찾는다. 여덟 개라 충분하다.

## 지키는 규칙

- 주문 본문에 가격, 금액, 주문자를 받지 않는다. 받는 순간 보내는 쪽이 정한다
- 재고 차감은 조건을 건 갱신 한 번이다. 읽고 나서 줄이는 코드로 바꾸지 않는다
- 재고 차감과 주문 저장은 한 트랜잭션이다. 저장이 실패하면 재고도 돌아온다
- 수량 검증은 재고 차감보다 먼저다
- 주문 조회는 언제나 토큰의 `sub` 로 좁힌다. 남의 주문번호는 404 다
- 화면의 가격과 재고는 서버 값만 찍는다. 프론트 배열에 다시 넣지 않는다

## 아직 없는 것

- **서비스별 권한.** 주문 API 는 역할(`CUSTOMER`)로 판정한다. `resource_access` 에 이 서비스의
  권한이 실리면 그것으로 바꾼다
- **결제, 취소, 배송.** `OrderStatus` 는 `PLACED` 하나다. 이 저장소의 주제가 아니다
- **장바구니.** 한 번에 상품 하나만 주문한다
- **상품 관리.** 상품은 마이그레이션 시드로만 들어간다. 가격이나 재고를 바꿀 화면이 없다
- **새로고침하면 로그아웃이다.** 토큰을 메모리에만 둔다([토큰을 어디에 두나](토큰을-어디에-두나.md))
