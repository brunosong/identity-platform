# 회원가입

계정을 만드는 길. 스스로 가입하는 것과 운영자가 등록해 주는 것으로 갈린다.

## 누가 가입할 수 있나는 realm 이 정한다

경로를 나누지 않고 realm 이 연다. `Realm` enum 이 그 정책을 들고 있다.

| realm | 비밀번호 가입 | 이메일 인증번호 가입 |
|---|---|---|
| `PORTAL` (고객) | 열림 | 열림 |
| `ADMIN` (직원) | **닫힘** | 열림 |

전에는 `/api/auth/customer/register` 와 `/api/auth/employee/register` 처럼 **경로 이름이 정책**
이었다. 그러면 realm 이 하나 늘 때마다 경로를 새로 만들어야 하고, 무엇이 열려 있는지 한눈에
보이지 않는다. 지금은 경로가 하나고 realm 이 연다.

닫힌 방식으로 들어오면 **404** 다. 403 이 아니다. "여기에도 가입 API 가 있긴 한데 막혀 있다" 를
알려줄 이유가 없다.

## 직원이 스스로 가입해도 되나

된다. 그리고 그것이 위험하지 않은 이유가 이 설계의 요점이다.

```
셀프 가입으로 생긴 신원  ->  역할이 하나도 없다  ->  로그인은 되지만 아무 문도 못 연다
```

기본 역할을 주는 리스너는 고객(`PORTAL`)만 상대한다. 직원 realm 에 만들어진 계정은 빈 껍데기이고,
쓸 수 있게 만드는 것은 여전히 `AUTHZ_MANAGE` 를 가진 운영자다. **신원을 만드는 일과 권한을 주는
일이 갈려 있다는 것**이 여기서 값을 한다.

## 한눈에 (고객, 비밀번호 가입)

```
  앱                       auth                             DB
   |                        |                               |
   |-- 이메일, 비번, 이름 -->|  같은 realm 에 아이디가 있나   |
   |   .../register         |  그 이메일의 신원이 이미 있나  |
   |                        |    있으면 -> 수단만 더한다     |
   |                        |    없으면 -> 신원 채번 ------->| identity_principal
   |                        |  비밀번호 계정 -------------->| identity_password_account
   |                        |  이메일 계정 ---------------->| identity_email_account
   |                        |  "생겼다" 이벤트 발행          |
   |                        |    -> 프로필 생성 ----------->| identity_principal_profile
   |                        |    -> 기본 역할 부여 --------->| authz_subject_role
   |<-- 201 principalId ----|  토큰은 주지 않는다            |
```

**가입은 토큰을 주지 않는다.** 가입과 로그인은 다른 일이고, 가입 직후 로그인시키려면 그것은
로그인 흐름을 한 번 더 타는 것이 맞다.

## 이메일이 하나면 신원도 하나

비밀번호로 가입하든 소셜로 들어오든, **같은 이메일이면 같은 신원에 수단만 늘어난다.**

```
신원 (Principal)
 ├─ 비밀번호 계정   (loginId + 해시)
 ├─ 이메일 계정     (인증번호 로그인용)
 └─ 소셜 계정       (구글)
```

그래서 비밀번호로 가입한 사람은 이미 이메일 인증번호로도 로그인할 수 있다. 가입 경로에서
이메일 계정을 함께 만들기 때문이다.

아이디 중복은 **같은 realm 안에서만** 따진다. 직원 `hong` 과 고객 `hong` 은 다른 계정이다.

## 가입이 부르는 것들은 한 트랜잭션이다

신원을 만들고 "생겼다" 는 이벤트를 발행하면, 프로필을 만드는 리스너와 기본 역할을 주는 리스너가
그 자리에서 돈다(`@EventListener`, 동기). 한 트랜잭션이라 **프로필이 안 만들어지면 가입도
되돌아간다.**

auth 는 누가 그 이벤트를 받는지 모른다. 그래서 가입 서비스 코드에는 "고객" 도 "프로필" 도 없다.
서비스가 쪼개지면 이 원자성은 saga 로 바뀐다.

기본 역할 리스너가 없거나 `CUSTOMER` 역할이 DB 에 없으면 **가입 자체가 롤백된다.** 로컬 시드가
그 역할을 넣어두는 이유다.

## 지키는 규칙

- **닫힌 가입 방식은 404.** 막혀 있다는 사실도 알리지 않는다
- **가입용 인증번호는 등록되지 않은 주소에만 나간다.** 로그인용과 조건이 정반대다
- **응답은 어느 쪽이든 202.** "이미 가입된 이메일입니다" 를 돌려주면 가입자 명단을 훑을 수 있다
- **아이디 중복은 realm 안에서만.** 유일성의 범위가 곧 격리의 범위다
- **가입은 토큰을 주지 않는다**

## 아직 없는 것

- **비밀번호 가입에서 이메일 소유 확인.** 지금은 확인되지 않은 상태로 들어간다. 그 계정은
  나중에 소셜로 들어올 때 자동 연결이 막히고, 연결 화면도 없어 막다른 길이 된다
- **탈퇴.** 신원 상태에 `WITHDRAWN` 자리는 있지만 그리로 보내는 길이 없다
- **가입 화면.** auth 가 그리는 가입 화면이 없다. 지금은 앱마다 자기 화면에서 API 를 부른다
- **약관 동의, 캡차.** 가입 절차에 끼울 자리가 없다
