# 회원가입

계정을 만드는 길. 스스로 가입하는 것은 auth 의 가입 화면에서 하고, 직원 계정은 관리자가 만든다.

## 왜 이렇게 하나

| | 전 | 지금 |
|---|---|---|
| 가입 화면 | 앱마다 자기 화면 (`SignUpPage`) | auth 가 그리는 화면 하나 |
| 비밀번호 | 앱을 거쳐 `/api/auth/realms/{realm}/register` 로 | 앱을 거치지 않는다 |
| 가입 뒤 | 201 만 받고, 로그인을 다시 해야 했다 | 로그인된 채로 앱에 돌아간다 (code) |
| 직원 셀프 가입 | 인증번호로 열려 있었다 | 닫혔다 |
| 이미 있는 이메일로 비밀번호 가입 | 그 신원에 비밀번호를 붙였다 | 거절한다 |
| 비밀번호 가입의 이메일 확인 | 없었다. 미확인으로 들어갔다 | 인증번호를 먼저 받는다 |

가입은 비밀번호를 처음 정하는 순간이다. 로그인은 auth 화면에서 받으면서 가입만 앱에서 받으면,
비밀번호가 앱을 거치지 않게 하려던 이유가 가입에서 다시 생긴다.

## 한눈에

```
  앱                          auth                                   DB
   |                            |                                      |
   |-- /auth?prompt=create ---->|  요청 검증, 가입 화면                 |
   |   (또는 로그인 화면의 [회원가입] -> /auth/register)                |
   |                  [1. 이메일, 이름, 전화번호]                     |
   |                            |  가입용 인증번호 발송 (미가입 주소만) |
   |                  [2. 인증번호, 비밀번호(선택)]                    |
   |                            |  번호 확인 -> 틀리면 다시 그림        |
   |                            |  이미 가입된 이메일인가 -> 거절       |
   |                            |  신원 채번, 수단 저장 -------------->| identity_*
   |                            |  "생겼다" 이벤트 -> 프로필, 기본 역할 >| authz_subject_role
   |                            |  인증 확정, 로그인 세션 심기         |
   |<-- 앱 주소?code=..&state= -|  로그인과 같은 끝                   |
```

## 왜 그렇게 도나

**앱은 `prompt=create` 만 쓴다.** 인가 엔드포인트에 표준 파라미터(OIDC Prompt Create)를 단 것이고,
발급자 문서의 `prompt_values_supported` 에 `none`, `create` 가 적혀 있다. `/auth/register` 는 로그인
화면과 가입 폼이 오가는 내부 주소라 앱이 가리키지 않는다. 바꿔도 앱이 모르게 두려는 것이다.

**가입이 곧 로그인이다.** `RegisterWith*UseCase` 가 가입한 사람(`AuthenticatedSubject`)을 돌려주고
인증 시각과 인증 이벤트를 남긴다. 화면은 세션을 심고 code 를 낸다. Keycloak 도 가입 뒤 바로 로그인된다.

**비밀번호로 가입해도 인증번호를 먼저 받는다.** 확인하지 않은 주소로 계정을 만들면 그 주소는 남의 것일
수 있다. 전에는 비밀번호 가입이 이메일을 미확인으로 남겨서, 그 사람이 나중에 구글로 들어오면 자동
연결이 막혔다. 이제 두 가입이 폼 하나로 합쳐졌다. 번호를 받은 다음 걸음에서 비밀번호를 적으면
비밀번호 계정까지 생기고, 비우면 인증번호로만 로그인하는 계정이 된다. 비밀번호를 첫 걸음에서 받지
않는 것은 화면 사이를 hidden 값으로 들고 다니지 않으려는 것이다.

이 확인이 걸음마다 어떻게 도는지, 경우마다 무엇이 보이는지는 [가입 이메일 확인](가입-이메일-확인.md)에
따로 적었다.

**번호부터 보고, 그다음에 가입 여부를 본다.** 순서가 반대면 주소의 주인이 아니어도 "이미 가입된
이메일" 이라는 답으로 누가 가입했는지 훑을 수 있다. 가입용 번호는 가입된 주소로 나가지 않으므로,
가입된 주소로 가입을 시도하면 번호 확인에서 끝나고 화면은 "번호가 맞지 않는다" 만 말한다. 번호를 받은
뒤 사이에 가입된 경우만 "이미 가입된 이메일" 로 거절한다. 전에는 이 경우 그 신원에 비밀번호를 붙여서,
남의 이메일을 적은 사람이 그 계정에 들어갈 수 있었다.

**직원 realm 은 닫혀 있다.** realm 이름은 주소창과 발급자 문서에 그대로 나와 숨길 수 없다. 열어 두면
아무나 직원 신원과 `aud=backoffice` 토큰을 얻고, 방어가 권한 검사 한 겹에 기대게 된다. 관리 API 하나가
권한 확인을 빠뜨리면 그대로 뚫린다. 아무 주소로 인증번호 메일을 보내게 하는 길이기도 했다.

## 누가 가입할 수 있나는 realm 이 정한다

| realm | 비밀번호 가입 | 인증번호 가입 | 계정이 생기는 길 |
|---|---|---|---|
| `PORTAL` (고객) | 열림 (번호를 받은 뒤 선택) | 열림 | 가입 화면 |
| `ADMIN` (직원) | 닫힘 | 닫힘 | 관리자의 직원 등록, 시드의 최초 관리자 |

가입은 언제나 인증번호로 시작하므로 인증번호 가입이 열려 있어야 가입할 수 있다. 비밀번호 가입이 열려
있으면 두 번째 걸음에 비밀번호 칸이 생긴다. `Realm.registrationMethods()` 가 비어 있으면 닫힌 것이다. 가입 화면과 폼은 404, `prompt=create` 는
오류 화면이고 로그인 화면에 회원가입 버튼이 뜨지 않는다.

## 지키는 규칙

- **가입 폼과 비밀번호는 앱을 거치지 않는다.** 가입 API 는 없다
- **인가 요청은 폼마다 다시 검증한다.** hidden 값이라 브라우저에서 고칠 수 있다
- **닫힌 방식은 404.** 막혀 있다는 사실도 알리지 않는다
- **가입용 인증번호는 등록되지 않은 주소에만 나간다.** 보냈는지 아닌지는 화면에서 가르지 않는다
- **가입으로 생긴 이메일은 언제나 확인된 주소다.** 비밀번호를 정해도 번호를 먼저 받는다
- **비밀번호는 번호를 받은 다음 걸음에서 받는다.** 화면 사이를 hidden 값으로 들고 다니지 않는다
- **번호 확인이 가입 여부 확인보다 먼저다.** 주소 주인이 아니면 가입 여부를 알 수 없다
- **아이디 중복은 realm 안에서만.** 직원 `hong` 과 고객 `hong` 은 다른 계정이다
- **가입과 이벤트 리스너는 한 트랜잭션이다.** `CUSTOMER` 역할이 없으면 가입이 통째로 롤백된다

## 아직 없는 것

- **로그인한 뒤 수단 더하기.** 인증번호나 구글로 가입한 사람이 비밀번호를 정할 길이 없다
- **탈퇴.** 신원 상태에 `WITHDRAWN` 자리는 있지만 그리로 보내는 길이 없다
- **약관 동의, 캡차.** 가입 화면에 끼울 자리가 없다
