# 권한 관리 화면

운영 화면(MASTER 로그인)에서 역할에 권한을 묶고, 사람에게 역할을 붙인다. 여기서 고친 것이 그 사람의
다음 토큰에 `realm_access`, `resource_access` 로 실린다. 세 층의 구조 자체는 [권한 관리](권한-관리.md) 에 있다.

## 왜 이렇게 하나

| | 전 | 지금 |
|---|---|---|
| 역할에 권한 묶기 | 시드 SQL 을 새로 쓰거나 관리 API 를 손으로 부른다 | `/page/roles/{roleId}` 에서 체크 |
| 사람에게 역할 붙이기 | 가입할 때 붙는 역할 말고는 DB 를 고친다 | `/page/subjects` 에서 찾아서 체크 |
| 권한이 토큰의 어느 칸으로 가나 | 표에서 `service_id` 를 직접 봐야 안다 | 화면이 서비스별로 묶어 보여 준다 |

토큰에 권한을 싣게 된 뒤로, 권한을 바꾸는 일이 곧 토큰을 바꾸는 일이 됐다. 그 손잡이가 SQL 뿐이면
"바꿨더니 토큰에 실린다" 를 확인할 길이 없었다.

## 한눈에 보는 흐름

```
운영자 (MASTER 로 로그인)
  |
  |  GET  /page/roles/{roleId}             그 realm 의 권한을 서비스별로 묶어 체크박스로
  |  POST /page/roles/{roleId}/permissions  체크한 것으로 통째로 바꾼다 ---> authz_role_permission
  |
  |  GET  /page/subjects?realm=&login=     이메일 계정 -> 없으면 비밀번호 계정의 로그인 아이디
  |                                         -> 신원(principal) -> subjectId -> 그 realm 의 역할
  |  POST /page/subjects/roles             체크한 것으로 통째로 바꾼다 ---> authz_subject_role
  |
  |  (저장하고 끝. 누구에게도 알리지 않는다)

그 사람의 다음 로그인, 또는 refresh
  auth 가 표를 다시 읽는다 --> realm_access.roles              <- 사람 -> 역할
                           --> resource_access.<서비스>.roles   <- 역할 -> 권한, service_id 로 묶음
```

## 왜 그렇게 도나

**저장하고 아무에게도 알리지 않는다.** 토큰은 발급할 때마다 표를 다시 읽는다. 바뀐 것이 퍼지는 길은
그것 하나다. 이미 나간 access 는 1분 안에 끝나고 refresh 때 새 값을 받는다. 화면 문구가 "다음 발급부터"
라고 말하는 이유다.

**권한을 서비스별로 묶어 보여 준다.** 서비스 이름이 곧 `resource_access` 아래 칸 이름이다. 체크한
권한이 토큰의 어느 칸으로 가는지 화면에서 바로 보여야 한다. 서비스가 없는 권한은 체크해도 토큰에
실리지 않아서 "서비스 없음" 으로 맨 뒤에 따로 둔다. 이 때문에 읽기 모델(`PermissionView`)에 `serviceId` 를 더했다.

**사람은 이메일이나 로그인 아이디로 찾는다.** 운영자는 subjectId 를 모른다. 로그인 계정 표에서 신원을
거꾸로 찾는다. 이메일 계정을 먼저 보고, 없으면 비밀번호 계정을 본다. MASTER 의 `admin` 처럼 이메일
없이 아이디만 있는 계정이 있어서다.

**통째로 바꾼다.** 체크박스 폼은 체크된 것만 보낸다. 무엇을 붙이고 뗄지 계산하지 않고, 온 목록을 그대로
새 상태로 삼는다. 하나도 체크하지 않으면 칸 자체가 오지 않으니 빈 목록으로 받는다.

## 지키는 규칙

- **화면에는 그 realm 의 역할과 권한만 내놓는다.** 서비스 계층이 realm 을 검사하지 않아서 지금은 화면이 유일한 울타리다
- **빈 체크는 "모두 뗀다" 다.** 칸이 안 왔다고 "그대로 둔다" 로 읽지 않는다
- **사람에게 권한을 직접 주는 화면을 만들지 않는다.** 권한은 역할을 통해서만 간다
- **저장 뒤에 토큰을 강제로 끊지 않는다.** 늦어도 access 수명(1분)만큼이다
- **새 화면도 `/page/` 아래에 둔다.** 운영 화면 체인이 그 아래를 MASTER 로그인 뒤에 둔다

## 아직 없는 것

- **realm 검사.** `ReplaceRolePermissionsUseCase`, `AssignSubjectRolesUseCase` 가 붙이려는 것이 같은 realm 인지
  보지 않는다. 폼 값을 손으로 만들어 보내면 다른 realm 의 권한이나 역할이 붙는다
- **운영자의 권한 검사.** 운영 화면은 MASTER 로그인만 보고 `AUTHZ_MANAGE` 는 보지 않는다. MASTER 에 로그인할 수 있으면 누구든 고친다
- **변경 기록.** 누가 언제 무엇을 바꿨는지 남지 않는다
- **소셜 계정만 있는 사람 찾기.** 이메일 계정도 비밀번호 계정도 없어서 찾을 수 없다
- **사람 목록.** 이미 아는 사람만 찾을 수 있다
- **권한 추가와 끄기 화면.** `/page/permissions` 는 아직 보기만 한다. 관리 API 로만 된다
- **local 밖에서 띄우기.** 운영 화면 컨트롤러가 모두 `@Profile("local")` 이다
